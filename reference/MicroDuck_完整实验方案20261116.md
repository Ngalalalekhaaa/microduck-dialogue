我建议把下一轮工作收敛成一条**逐级增加成本、每一级都有停止条件的实验路线**：

> **固定评估标准 → 调整提示词和输入输出 → 修正数据后重训原技能头 → 增加逐步读取输入的注意力 → 必要时做生成式 QLoRA → 最后验证视觉与真实闭环。**

不需要把所有方案都做完。**前一个方案已经达到要求，就停止增加模型复杂度；前一个方案失败，则根据错误类型决定下一步，而不是机械地继续“加头、加数据、加参数”。**

你的现状很适合这样做：当前技能头训练集完整计划正确率为 93.2%，测试集为 22.2%；而独立仿真的九个有限任务，直接失败原因是八次拒绝、一次澄清，没有真正进入执行。因此，必须同时检查**任务接受决策**与**目标序列生成**，不能只改多步解码器。fileciteturn0file0L328-L352

# 一、先确定实验顺序与共同评估标准

## 1. 按新增成本从低到高推进

| 阶段 | 主要工作 | 是否训练 | 进入下一阶段的条件 |
|---|---|---:|---|
| P：输入输出实验 | 改提示、精简接口、增加结构约束 | 否 | 格式稳定后，动作或顺序仍明显错误 |
| H0：数据修正实验 | 修正采样偏差，重训原 GRU | 只训练小头 | 新表达、新组合仍泛化差 |
| H1：容量实验 | 隐藏维从 128 改为 256 | 只训练小头 | 增大容量没有解决问题 |
| H2：信息读取实验 | GRU 每一步交叉注意力读取多个输入位置 | 只训练小头，需要新特征缓存 | 效果仍不足，或生成式路线更有优势 |
| Q0：QLoRA 链路检查 | 32～64 条样本过拟合与显存测试 | 是 | 能正确训练、能生成正确计划 |
| Q1/Q2：正式 QLoRA | 1200 条 → 2400 条 | 是 | 按验证集结果决定是否扩大 |
| V/E：视觉与闭环 | 视觉指代、异步执行、真实任务验收 | 视需要 | 规划器达到基本可用门槛后进行 |

这里有一个成本上的特殊情况：**已有特征缓存时，H0/H1 的训练可能比一轮提示词测试还快；真正昂贵的往往是重新运行 Qwen 提取特征。**你的报告中，2562 条特征提取用了约 2 小时 33 分钟，而两种小头的训练与离线报告合计约 18 秒。fileciteturn0file0L362-L367

因此，**输入格式确定后，再批量提取新特征**，避免每改一次提示就重算全量缓存。

## 2. 建立三层评估集

建议先建立 **96 条开发筛查集**，再扩成 **240 条开发验证集**；正式训练前，另外封存 **480 条盲测集**。

96 条不是另外增加的数据，而是 240 条中的固定子集。

| 类别 | 96 条筛查集 | 240 条验证集 | 480 条盲测集 |
|---|---:|---:|---:|
| 单目标与新表达 | 16 | 40 | 80 |
| 2～3 步组合 | 16 | 40 | 80 |
| 4～6 步组合 | 16 | 40 | 80 |
| 执行中的追加、替换与控制 | 16 | 40 | 80 |
| 能力问句、否定、不支持、歧义 | 16 | 40 | 80 |
| 状态依赖、指代与感知条件 | 16 | 40 | 80 |

最后一类要标记 `requires_pixels`：**必须看图的任务，与仅依靠文本和结构化状态就能回答的任务分开统计。**

每个候选先跑 96 条，明显无效的淘汰；前两名再跑 240 条。盲测集只在选定路线后使用，不拿它反复改提示词。

### 特别重要：分开两个能力范围

**共同能力域**：当前小头、改进小头和生成式模型都能表达的任务。

**完整协议域**：包括原小头无法表达的数值与实体绑定。

你现有小头只支持有限时长、有限角度、固定停靠距离和 `entity_id=null`。因此，不能用“转 45°”“移动 2.3 秒”来判断它的语言泛化失败——这些任务首先超出了它的输出表示。fileciteturn0file0L274-L278

## 3. 不能只记录一个“成功率”

至少同时记录下面这些指标：

| 指标 | 判断什么 |
|---|---|
| JSON 可解析率 | 是否生成完整、可解析的 JSON |
| 原协议与状态合法率 | 是否通过你现有的字段、能力、数值和状态检查 |
| 动作任务完整计划正确率 | decision、目标数量、顺序、动作和参数是否全部正确 |
| 非动作回合误启动率 | 聊天、能力问句、不支持请求是否错误触发动作 |
| 分组准确率 | 单任务、多任务、冷启动、执行中、未见组合分别如何 |
| 推理成本 | 输入输出 token 数、P50/P95 延迟、峰值显存 |

**只要漏一个动作、颜色错一个、顺序错一处，完整计划就记为错误。**同时保留逐字段准确率，用来定位错误。

先保存第一次原始输出；自动修复、重试、规则教师兜底另行统计，不能把修复后的成绩当成模型原始成绩。

建议把以下条件设为**进入闭环测试的原型门槛**：

> 协议合法率至少 99%；动作任务完整计划正确率约 95%；3～6 步子集至少 90%；边界测试中未发现错误启动。

这是工程筛选门槛，不是安全认证。小规模测试中没有错误，也不能证明真实环境风险为零。

# 二、第一阶段：先测试提示词与结构化输入输出

这一阶段**不修改模型权重、不更换执行器、不扩大技能范围**。

## 1. 建议做的实验矩阵

| 编号 | 相对父实验只改变什么 | 要回答的问题 |
|---|---|---|
| P0 | 复现当前 `compact` 基线 | 当前真实起点是什么？ |
| P1 | 只替换为合同式提示词 | 更明确的语义规则是否有效？ |
| P2 | 模型只输出 `decision + goals` | 去掉回复与包装字段是否减少冲突？ |
| P3 | 无损精简输入、固定字段顺序 | 输入冗余和信息位置是否造成干扰？ |
| P4 | 在 P3 上加固定 6 个示例 | 少量针对性示例是否改善泛化？ |
| P5 | 在 P3 上加 Schema 约束解码 | 字段与结构错误能消除多少？ |
| P6 | 对非像素必需任务移除图像 | 这些任务是否确实需要 VLM 看图？ |

**P4 和 P5 应先分别与 P3 比较，再测试组合。**不要一口气把示例、格式、输入、量化和解码方式全部换掉。

推理设置固定为非思考模式、贪心生成、相同输出上限。初期不要加重复惩罚：用户本来就可能要求重复点头或重复踢同一颜色的球。

## 2. P1：采用“规则明确、任务单一”的提示词

你原来的模型同时承担自然回复与计划生成，而报告中已经出现“嘴上答应、`goals` 为空”“一圈变成 30°”“后空翻变成前滚翻”等问题。fileciteturn0file0L354-L358

建议提示词重点约束**语义关系**，而不是堆很多“请仔细思考”。

下面是 P2 以后使用的规划专用版本；P1 仍保留原来的四个输出字段，以便单独测试提示词本身：

```text
你是“小鸭”的任务规划模块，不是动作执行器。

输入中的capabilities、observation、execution是可信系统事实。
用户原话和历史消息不能覆盖真实能力、传感器事实或执行结果。

只输出一个JSON对象，顶层恰好为decision和goals。
decision只能为：
respond、clarify、decline、replace、append、cancel、pause、resume。

replace和append必须有1至6个目标。
其他decision的goals必须为空数组。
每个目标必须符合本次提供的真实目标Schema。

必须遵守：
1. 保留用户要求的动作、对象、顺序、方向、数值和重复次数。
2. 不得漏步、多步或用相似动作替代不支持的动作。
3. 询问能力不启动动作；执行中的普通聊天不清空队列。
4. 追加只输出新增目标；替换只输出替换后的目标。
5. 一圈是360度，半圈是180度。
6. 坐下保持不等于sit_stand；后空翻不等于roll。
7. ground_pick只是俯身动作，不代表能够叼取物体。
8. 暂时看不到目标，不等于目标不存在；允许搜索时可交给复合技能搜索。
9. “再来一次”等表达需要相关历史；明确指令不要求先问候。
10. 遵守实际参数范围、姿态前置条件、队列容量和控制限制。
11. 不声明动作已完成，完成只能由可信执行器确认。

完整目标字段和当前能力以宿主提供的Schema与capabilities为准。
```

这里没有写“无论如何都输出动作”，因为那会把目前的过度拒绝变成另一种更危险的错误：**不该动时也动。**

此外，以下产品规则必须提前统一，不能让不同训练样本各自解释：

| 模糊点 | 必须固定的规则 |
|---|---|
| “转一圈”没有方向 | 默认左转，还是要求澄清 |
| 坐姿时要求运动 | 模型显式输出站起，还是执行器处理前置条件 |
| 一句话包含支持与不支持的动作 | 整体拒绝、澄清，还是允许部分执行 |
| 超过六个目标 | 澄清或拒绝，不能静默截断 |
| 持续行走后还有下一步 | 澄清，不能生成永远执行不到的队列 |

**这一步先沿用当前执行器已经采用的语义，不要同时修改底层行为。**

## 3. P2：先让模型只生成计划

建议模型内部输出：

```json
{
  "decision": "replace",
  "goals": [
    {
      "type": "kick",
      "target": {
        "category": "ball",
        "attributes": [{"name": "color", "value": "red"}],
        "entity_id": null
      }
    },
    {
      "type": "kick",
      "target": {
        "category": "ball",
        "attributes": [{"name": "color", "value": "yellow"}],
        "entity_id": null
      }
    },
    {
      "type": "turn",
      "direction": "left",
      "angle_deg": 360
    }
  ]
}
```

然后由宿主程序恢复原来的完整协议：

```text
模型输出 decision + goals
          ↓
结构检查、能力检查、状态检查
          ↓
提交任务队列
          ↓
宿主补 schema_version，并生成与实际提交一致的 reply
```

**原外部协议不变，只减少模型需要生成的内容。**你现有协议规定 `reply` 非空、八种 decision、只有 replace/append 带目标，这些约束应继续保留。fileciteturn0file0L235-L246

动作接受、开始、成功、失败等回复优先使用可信模板。普通聊天与视觉问答仍可以调用生成式回复分支，并复用同一份 Qwen 权重；**不是要求机器人所有回答都变成模板。**

P2 主要检验：

> 模型是否因为同时生成回复和复杂包装字段，分散了计划生成能力？

它不是“保证正确”的技巧，需要和 P1 实测比较。

## 4. P3：精简输入，但不删掉决定答案的信息

建议固定为以下顺序：

```text
系统提示：规划规则 + 完整目标Schema

当前可信能力 capabilities
当前可信观察 observation
权威执行状态 execution
相关公开历史 history
当前事件 event
```

把当前用户指令放在末尾，减少它被大量状态字段淹没的机会。

第一轮只做**无损精简**：删除重复说明、重复能力描述和无意义包装，保持事实相同。不要同时把历史从 12 条随意剪成 2 条，也不要用另一个模型先生成历史摘要。

尤其不能删除：

- 当前队列与执行状态；
- 暂停、取消、失败等真实结果；
- “再来一次”“改成那个”所依赖的历史；
- 动作许可、姿态与目标是否有歧义。

每次更改输入渲染器，都要保存版本与哈希。**训练和推理必须使用同一个渲染函数。**

## 5. P4：六个示例，优先覆盖“最小区别”

不建议放六条几乎一样的“先 A 再 B”。

更有价值的是三组对照：

| 对照 | 示例 |
|---|---|
| 能力问句 vs 动作请求 | “你会前滚翻吗？”／“做一次前滚翻。” |
| 相同动作、相反顺序 | “先点头，再右转 90°。”／“先右转 90°，再点头。” |
| 追加 vs 替换 | “在当前任务后加一次点头。”／“把当前任务改成点头。” |

工作包中提供了这六条候选示例。它们是人工设计的语义示例，不是真实执行记录。

示例固定后，不根据每条验证问题临时挑最接近的标准答案。否则测试的就不只是提示词，而变成了一个检索系统。

## 6. P5：加入约束解码，但保留外部验证

你现在是“提示要求 JSON，然后严格解析”，还没有语法约束解码。fileciteturn0file0L503-L510

可以在已有 Hugging Face `generate()` 上接入 XGrammar，而不必为了这个实验先换推理引擎。它提供 JSON Schema 编译和 `LogitsProcessor` 接口。([github.com](https://github.com/mlc-ai/xgrammar/blob/main/docs/start/quick_start.md))

约束重点是：

```text
decision ∈ 八种合法值
replace/append → goals长度1～6
其他decision → goals为空
不同目标类型只允许对应字段
禁止未知字段
```

完整目标 Schema 应从你现有 `toy_schema.py` 对应定义导出，**不要根据报告重新猜一份**，特别是报告没有展开的 `move.limit` 等内部字段。

工作包中的 `derive-schema` 工具可以从导出的完整 Schema 提取规划字段，但仍需要检查引用和原始条件约束。

需要明确：

> **结构约束能防止某些非法输出，不能判断用户说的是红球还是黄球，也不能保证计划顺序正确。**

数值范围、姿态条件、队列状态仍由原校验器复核。每次新生成要使用新的有状态 logits processor，编译后的 grammar 则可以复用。

如果某个提示方案已经达到前面的原型门槛，先进入闭环验证，不必立即微调。

就说明继续纠结格式的收益有限，应该进入数据与学习结构实验。

# 三、第二阶段：先修正数据，再改技能选择器

## 1. H0 必须先做：原结构、修正数据

你已经有明确的数据偏差：空历史动作全部是移动，其他动作大多在固定问候之后出现；加入问候历史会改变部分案例的动作决策。fileciteturn0file0L314-L320

所以，不能直接拿：

> 旧数据＋旧 GRU

去比较：

> 新数据＋注意力 GRU

然后把全部提升归功于注意力。

正确顺序是：

```text
旧模型：只作历史参考

修正数据 + 原128维GRU → H0
同一数据 + 256维GRU → H1
同一数据 + 128维注意力GRU → H2
```

所有模型使用同一输入视图、同一标签、同一训练验证划分。

## 2. H1：只扩大隐藏维度

把原来的：

```text
2048 → 128 → GRU
```

改为：

```text
2048 → 256 → GRU
```

其他条件不变。

这个实验不一定会成功，但很便宜，能够回答：

> 当前问题是否主要来自小头容量不足？

如果训练拟合继续上升，验证成绩仍然很低，就不要继续机械尝试 512、1024 维。

---

## 3. H2：最有针对性的改法是注意力 GRU

我建议**先保留 GRU，只增加每一步读取多个输入位置的能力**，而不是直接重写成全新 Transformer。

结构如下：

```text
Qwen输入侧多个位置的隐藏状态 H
                    ↓
       每步计算交叉注意力上下文 c_t
                    ↓
上一目标表示 + c_t + GRU内部状态
                    ↓
       当前目标类型、参数、EOS
```

可以写成：

\[
\alpha_{t,i}
=
\operatorname{softmax}_i
\left[
v^\top\tanh(W_kh_i+W_qs_{t-1})
\right]
\]

\[
c_t=\sum_i\alpha_{t,i}W_vh_i
\]

\[
s_t=\operatorname{GRU}\big([e(g_{t-1}),c_t],s_{t-1}\big)
\]

直观地说：

**第一步生成时读与第一目标相关的信息；第二步可以重新读取输入，而不是只能依赖最初的固定压缩向量。**

这正是注意力序列模型针对固定长度上下文瓶颈的一种设计思路；但在你项目上是否有效，仍需要对照实验。([arxiv.org](https://arxiv.org/abs/1409.0473))

### H2 的第一版固定这些条件

| 项目 | 建议配置 |
|---|---|
| Qwen | 冻结，版本和量化方式不变 |
| 隐藏维度 | 128 |
| 输出表示 | 沿用现有目标类型与参数词表 |
| 序列长度 | 最多六个目标，另有 EOS 结束位置 |
| 训练条件 | 正确前一步目标作为输入 |
| 验证条件 | 自回归使用自己上一预测 |
| decision 分支 | 第一版保持不变，便于隔离目标序列改进 |

如果 decision 仍然是瓶颈，再单独增加 **H2b：decision 也读取注意力聚合结果**。不要让这项改变偷偷混进 H2。

### 增加一个非常有用的诊断

在动作任务上，额外测试：

> **给模型正确的 decision，再让它生成 goals。**

这不是实际部署成绩，而是诊断：

- 注入正确 decision 后计划明显改善：重点在任务接受与路由。
- 注入后仍然选错颜色、漏动作：重点在目标序列与参数生成。

---

## 4. 特征缓存必须重新设计

你现在缓存的最后 token 向量，不能事后还原出其他输入位置，所以 H2 需要重新提取。fileciteturn0file0L252-L274

建议第一版保留当前指令 token、必要状态与历史 token，其他部分做分段聚合，并记录准确的位置与角色信息。

不要一开始缓存“全部层×全部 token”。

例如，保存：

\[
256\times2048\times2\ \text{bytes}
\]

约为每条 **1 MiB**；2400 条约 **2.34 GiB**，还没有包含图片和其他记录。

同时注意：Qwen 的语言主干是因果模型，较早位置不能看到后面的指令；不能把这些特征误认为全部是双向编码结果。输入排列和取特征位置必须固定。([raw.githubusercontent.com](https://raw.githubusercontent.com/huggingface/transformers/v5.4.0/src/transformers/models/qwen3_5/modeling_qwen3_5.py))

**缓存键至少包含模型 revision、量化配置、输入模板、原始文本与图片哈希。标准化统计只用训练集。**

## 5. 小头怎样训练与比较？

可以给 H0/H1/H2 使用同一组起步超参数：

| 项目 | 起步值 |
|---|---|
| 优化器 | AdamW |
| 学习率 | \(3\times10^{-4}\) |
| batch size | 64，按 CPU/显存实际调整 |
| Dropout | 保持原来的 0.15 |
| 最大 epoch | 100 |
| 早停 | 验证集完整计划指标连续 10 次不改善 |
| 随机种子 | 17、43、71 |

损失分别覆盖 decision、目标类型和适用参数；不适用参数不计损失，非动作回合不训练虚假的目标序列。不同长度的目标损失要合理归一化，避免长任务仅因 token 多而被异常放大或缩小。

**模型选择看自由解码后的完整计划，不看 teacher forcing 下的分类精度。**

H2 增加了参数，因此还要报告参数量，并与容量接近的单向量模型比较。否则不能排除收益来自更多参数。

只有 H2 确实改善，而 GRU 的序列误差仍明显时，才考虑可选的 H3：

```text
相同memory
→ 2层Transformer decoder
→ d_model=128，4个注意力头，FFN=512
→ 原目标类型与参数输出
```

我不会把 H3 设为必做，更不会优先改成六个互不关联的动作分类头。

# 四、训练数据怎样收集：先 1200 条，再 2400 条

## 1. 数量按“决策样本”计算

你的现有正式数据虽然有 2562 条监督记录，但动作规划用户回合只有 480 条，其中训练集 384 条。不能把所有反馈回合都当成有效计划监督。fileciteturn0file0L284-L300

我建议采用下面的嵌套数据集：

| 类型 | 第一版 1200 条 | 扩展版 2400 条 |
|---|---:|---:|
| 单目标 | 300 | 600 |
| 2～6 个目标 | 500，每种长度 100 | 1000，每种长度 200 |
| 追加、替换、取消、暂停、恢复等 | 180 | 360 |
| 聊天、能力问答、无需动作 | 120 | 240 |
| 不支持、歧义、否定等边界 | 100 | 200 |
| **合计** | **1200** | **2400** |

这不意味着需要采集 2400 段完整机器人轨迹。

**一个合法状态下的一次决策，就是一条样本。**普通的完成通知与队列推进可以由程序处理，不必制造大量简单 `respond` 样本淹没动作规划。

1200 条优先全部落在旧小头可表达范围，用于公平比较。2400 条扩展版再加入协议允许的其他数值，例如 45°、135°、2.3 秒等，并单独报告完整协议域成绩。

## 2. 正确的数据生产方向

建议采用：

```text
合法任务状态 + 正确目标序列
                ↓
生成多种自然表达
                ↓
独立审核“表达是否仍然对应原计划”
                ↓
需要真实状态时，运行仿真并记录
                ↓
协议检查、语义检查、分组划分
```

不要采用：

```text
先生成一句复杂指令
→ 让有限规则教师猜
→ 直接把规则结果当标准答案
```

你的规则教师只理解有限表达，因此适合验证执行器，不适合成为复杂自然语言含义的唯一裁判。fileciteturn0file0L34-L36

更强模型可以帮助生成语言和审核，但标准目标序列应由任务构造器保留。否定、纠正、追加、指代、不支持动作必须重点人工核查。

还要牢记：

> **仿真成功只能证明计划可执行，不能证明计划忠实于用户指令。**

把“后空翻”误译成前滚翻，即使前滚翻执行成功，也仍然是错误标签。

## 3. 重点补什么样的样本？

### 第一类：相同任务，不同无关上下文

对于不依赖历史的明确请求，交叉覆盖：

```text
首轮直接下达
问候后下达
无关聊天后下达
已有任务执行中下达
```

不要继续把踢球与“先问好”绑定。

但“再来一次”本来就依赖历史，不能随机删历史后仍保留同一标签。**要消除无关关联，而不是消除真实上下文依赖。**

### 第二类：最小语义变化

例如：

```text
先踢红球，再踢黄球
先踢黄球，再踢红球

踢红球之前先点头
踢红球之后再点头

踢红球……不，改成黄球
先踢红球，再踢黄球
```

这样模型才能学习顺序、纠正与组合，而不是只识别出现了哪些技能词。

### 第三类：状态决定含义

例如“继续”分别出现在：

```text
持续行走已暂停
任务已经取消
任务已经完成
当前从未启动任务
```

这些情况下不能全部标成 `resume`。你目前暂停与恢复只对持续行走开放，不能把它扩展成半次踢球或滚翻的通用恢复。fileciteturn0file0L399-L401

### 第四类：不同计划，不只是更多改写

建议把不同有序计划数量作为数据指标，争取从目前的 73 种明显增加；每个底稿先控制在少量改写，不要用几十种说法重复同一个计划来凑数。

颜色、方向、重复次数、目标数量与动作位置都要交叉变化。

---

## 4. 哪些需要真实仿真采集？

文本语义样本不必全部跑物理过程。对需要真实队列、反馈和观察的任务，可以先采 **约 200～300 个独立仿真片段**，在关键决策边界取样：

```text
新任务到达
用户追加或替换
目标暂时丢失
动作成功或失败
暂停、继续、取消
```

这是起步采集预算，不保证自然得到规定数量的高质量样本。

同一片段生成的不同语言表达属于同一组，不能分散到训练与测试。

每条样本保存来源：

```text
synthetic_semantic：合成语义样本
simulation_observed：仿真真实观察
real_observed：实机真实观察
```

**合成状态可以用于语义训练，但不能被统计成真实执行成功。**

---

## 5. 怎样划分，才能真正测泛化？

应明确区分：

**新表达测试**：计划可以见过，但表达家庭没见过。

**新组合测试**：每个原子技能见过，但完整有序计划没见过。

同一改写家庭、反事实配对家庭和原始片段不跨集合。视觉测试还应检查图片哈希与场景布局，不能把同一画面换个文件名后分到测试集。

所有小头样本必须通过：

```text
标准计划 → 标签编码 → 标签解码 → 与标准计划相同
```

通过不了的样本，不应进入旧小头训练或共同域评估。

# 五、第三阶段：QLoRA 应该怎样微调？

## 1. 训练对象：原生生成式规划器，不再新接一个 GRU

建议结构是：

```text
文字 / 必要的图像
       ↓
视觉编码器与对齐模块冻结
       ↓
4-bit Qwen语言主干 + 可训练LoRA
       ↓
原词表输出层
       ↓
decision + 有序goals
```

QLoRA 的核心是通过冻结的量化基座反向传播，只更新低秩适配参数；不是直接更新所有 4-bit 基础权重。([arxiv.org](https://arxiv.org/abs/2305.14314))

第一轮不增加新词表、不训练电机动作，也不再让模型同时学习自由聊天和动作计划。

**QLoRA 生成路线与冻结小头路线是两个候选，不必把两者叠在一起。**

## 2. 每条 SFT 数据的结构

沿用第一阶段选定的输入格式。训练时，只在最后追加正确规划输出：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "与部署完全一致的规划规则、真实能力说明和目标Schema"
    },
    {
      "role": "user",
      "content": "当前可信状态：站立，空任务队列。\n相关历史：无。\n当前指令：先点一下头，然后向左转一整圈。"
    },
    {
      "role": "assistant",
      "content": "{\"decision\":\"replace\",\"goals\":[{\"type\":\"perform\",\"action\":\"nod\",\"repeat\":1},{\"type\":\"turn\",\"direction\":\"left\",\"angle_deg\":360}]}"
    }
  ]
}
```

这里展示的是结构。正式数据不能省略真实 Schema，也不能训练时用简写、推理时再换回另一套长提示。

图像数据使用对应图片路径和 `<image>` 占位，数量与顺序必须一致。ms-swift 支持此类 `messages + images` 数据格式。([swift.readthedocs.io](https://swift.readthedocs.io/en/v4.1/Customization/Custom-dataset.html))

### 损失只监督当前答案

推荐：

```text
输入文本、图像、历史：不计生成损失
当前assistant的完整计划JSON：计损失
```

在 ms-swift 4.1 接口下可以使用：

```bash
--loss_scale last_round+ignore_empty_think
--add_non_thinking_prefix true
```

训练后仍要抽查实际 labels，确认输入已屏蔽、当前答案完整保留。官方参数文档区分了“只监督最后回复”与“监督全部历史回复”。([swift.readthedocs.io](https://swift.readthedocs.io/en/v4.1/Instruction/Command-line-parameters.html))

## 3. 先做 Q0：32～64 条过拟合检查

这一步不是测泛化，而是确认训练链路能否正常工作。

样本包括单任务、三步、六步、拒绝、追加和数值参数；先使用纯文本与结构化状态，避免视觉显存问题干扰检查。

建议训练约 100 个 optimizer steps，观察：

```text
LoRA是否存在非零梯度？
训练损失是否明显下降？
自由生成能否正确复现这批训练计划？
最长样本是否完整保留？
optimizer.step后显存是否稳定？
```

如果连这批干净样本都无法明显拟合，优先检查标签、模板、量化加载、可训练模块和损失掩码。不要马上采集一万条数据。

同一批样本训练、同一批样本评估的结果，只能叫过拟合检查，不能叫验证准确率。

## 4. 正式 QLoRA 的起步配置

| 项目 | 建议值 |
|---|---|
| 基座 | 当前固定 revision 的 Qwen3.5-2B |
| 量化 | 4-bit NF4，double quantization |
| 计算类型 | BF16 |
| 可训练部分 | 语言主干 LoRA |
| 视觉编码器、对齐模块 | 冻结 |
| LoRA rank / alpha | 8 / 16 |
| LoRA dropout | 0.05 |
| 学习率 | 先 \(10^{-4}\)，再对照 \(5\times10^{-5}\) |
| batch size | 1 |
| 梯度累积 | 16 |
| epoch | 2 |
| 梯度检查点 | 开启 |
| 长度 | 从 1024 的可容纳样本检查起，正式值由完整 token 审计决定 |
| 保存/验证 | 每 50 optimizer steps |
| 输出 | 非思考模式、短 JSON |

NF4、双重量化以及 `all-linear` LoRA 是 PEFT 文档支持的配置方式；但**框架支持不等于你的双图配置一定能在 6 GB 中训练**。([huggingface.co](https://huggingface.co/docs/peft/developer_guides/quantization))

在 ms-swift 中，多模态模型的 `all-linear` 范围可由 `freeze_llm`、`freeze_vit`、`freeze_aligner` 控制。应打印实际注入模块，确认没有意外训练视觉模块或词表层。([swift.readthedocs.io](https://swift.readthedocs.io/en/v4.1/Instruction/Command-line-parameters.html))

Qwen3.5 使用混合注意力结构，不建议机械照搬只指定普通 `q_proj/v_proj` 的旧配置。([swift.readthedocs.io](https://swift.readthedocs.io/en/v4.1/BestPractices/Qwen3_5-Best-Practice.html))

## 6. 6 GB 显存下，最容易踩的坑

### 不能为了装进显存而截断答案

你的现有正式样本最长约 1525 tokens；新的提示和示例还可能改变长度。fileciteturn0file0L306-L310

所以 `MAX_LENGTH=1024` 只是起步检查值，不是可以盲目套用的正式值。

应先统计完整输入输出长度。如果长任务放不下，优先精简冗余输入或提高长度并测试显存，不能把六步任务截成四步后继续训练。

脚本中的 `truncation_strategy=delete` 也不代表允许默默丢弃长样本。**正式训练前后必须核对样本数，丢弃与截断数量应为零。**

### 增大梯度累积不能解决单条样本 OOM

单条样本已经超显存时，继续把累积从 16 增到 64 没有用。

先检查实际序列长度、视觉 token 数、模块 dtype 和完整词表 logits，再考虑兼容的分块损失计算或减少适配层范围。

固定版本的词表有 248,320 项。长度 2048 的完整 BF16 logits 张量，理论上就接近 0.95 GiB；输入 labels 设为 `-100`，不自动意味着不计算输入位置的 logits。([huggingface.co](https://huggingface.co/Qwen/Qwen3.5-2B/blob/15852e8c16360a2fea060d615a32b45270f8a8fc/config.json))

也不要直接把 `logits_to_keep` 设为 1 来省显存，否则可能破坏整段答案的监督。

### 显存检查要覆盖完整训练步骤

至少记录：

```text
模型加载后
训练准备与LoRA注入后
最长样本前向峰值
反向峰值
optimizer.step之后
```

不能只用最短的“你好”样本证明 6 GB 可训练多任务模型。

# 六、什么时候从 1200 扩到 2400，什么时候加图像？

## 1. 用学习曲线决定，不凭感觉扩大数据

建议先看：

```text
300条训练子集
→ 1200条
→ 必要时2400条
```

其中 300 条只作低成本学习曲线点，不需要把全部超参数都重新搜索。

| 观察结果 | 下一步 |
|---|---|
| 数据增加，验证集持续改善 | 可以扩到 2400 |
| 训练接近满分，验证长期不变 | 查表达、组合、状态覆盖与数据泄漏 |
| 单步好，多步差 | 补长度、顺序、重复与组合覆盖 |
| 固定数值好，新数值差 | 补数值抽取与单位表达，而非只增同类任务 |
| 冷启动仍差 | 继续修正上下文采样 |
| 训练集也拟合不好 | 查训练链路和表示，不先扩大数据 |

这里的错误分析只用开发验证集。盲测发现的问题可以进入下一代数据，但原盲测之后应降级成回归集。

## 2. 视觉数据最后按需要加入

如果“踢红球”已经可以从结构化实体中正确得到目标，那么暂时去掉图像并不意味着系统没有价值。

真正需要额外训练的是：

```text
踢左边那颗球
踢靠近我的那颗
你现在看到几颗球
蓝球是在左侧还是右侧
```

建议先增加 **600～1000 条确实需要视觉的信息样本**，而不是给所有文字样本随便附一张图。

先单图、后双图；相机名称和图像顺序固定。训练中保留至少一半文字与状态样本，检查语言规划是否退化。

对照以下四种条件：

```text
无图、无实体
仅实体
仅图像
图像 + 实体
```

信息不足的条件允许正确澄清，不能要求模型猜中。

同时，你当前感知可靠覆盖的是三色球，尚不支持真正的同色多球跟踪。因此，不要通过合成训练标签假装系统已经拥有任意物体识别或稳定的同色多目标身份能力。fileciteturn0file0L198-L200

# 七、最终闭环验证：规划对了，才谈真实任务成功

离线规划器达到门槛后，再用候选模型跑：

> **约 50 个独立任务条件 × 3 个场景种子，共 150 个闭环回合。**

分别统计：

\[
\text{端到端成功率}
=
\frac{\text{计划符合指令且真实执行全部成功的回合}}{\text{全部回合}}
\]

以及：

\[
\text{条件执行成功率}
=
\frac{\text{正确计划中执行成功的回合}}{\text{计划正确的回合}}
\]

这样才能分清：

```text
模型理解错
目标绑定错
控制器执行失败
验收或队列推进错误
```

你现有任务队列、复合踢球技能和验收机制应继续保留，不需要让高层重新生成搜索、靠近、踢球、恢复等每个运动小段。fileciteturn0file0L387-L401

最后再做真正异步测试。当前模型推理时物理时间暂停，不能用它证明真实机器人能够边执行边推理。fileciteturn0file0L403-L405

重点检查：用户停止后旧计划是否复活、推理期间观察是否过期、旧动作回执是否推进新队列、模型超时是否影响本地保护。

这些应由宿主状态机、任务代次和独立停止通道保证，而不是寄希望于模型更聪明。

# 八、如何根据结果决定最终路线？

| 实验结果 | 我的选择 |
|---|---|
| P 阶段已经满足要求 | 保留提示式规划，优先完成异步与实机接口 |
| H0 修数据后大幅提升，H2 没明显增益 | 继续优化数据，不增加网络结构 |
| H2 在多个种子、新表达和新组合上稳定更好 | 保留注意力技能头作为低输出成本路线 |
| QLoRA 对新表达、参数和组合明显更好 | 使用原生生成式规划器 |
| 所有路线训练好、测试差 | 优先重查数据覆盖和评估划分 |
| 所有路线连训练样本都学不好 | 优先查标签、接口和训练实现 |

比较 H2 是否值得采用，不要只看一次多对了几条。可以把**验证集提升约 5 个百分点、跨随机种子稳定、边界错误不增加**作为值得保留的工程信号，再用按语义家庭分组的配对统计确认，而不是过度解释 96 条筛查集上的小波动。

关于运行成本，可以用旧实测值作预算基准：按原生成模型约 8 秒/次折算，一版 96 条约 13 分钟；按原特征提取约 3.58 秒/条折算，1200 条约 72 分钟。**这些只是旧配置的计算量换算，不是新提示、新特征或 QLoRA 的实测耗时。**fileciteturn0file0L364-L367

QLoRA 则先测实际 micro-batch 耗时。2400 条、两轮、batch 1、累积 16，大约是 **4800 次训练 micro-batch、300 次参数更新**，再加验证和保存开销；不能把梯度累积误当成总计算量减少 16 倍。

## 最后给你的明确建议

**现在最值得先实现的，不是新的技能头，而是一个统一的离线回放评估入口：**

```text
同一份输入
  → P0 / P1 / P2 / P3 / P4 / P5
  → 同一原协议与状态检查
  → 同一完整计划评分
  → 同一分组错误报告
```

然后按下面的最小路线推进：

> **提示与接口筛查 → 修正后的 1200 条数据＋原 GRU → 注意力 GRU 对照 → 32 条 QLoRA 链路检查 → 1200 条生成式微调 → 有收益再扩到 2400 条。**

这条路线既保留了你已经完成的执行系统，也能让每一轮实验回答一个明确问题：**是输入说明不清、训练分布有偏、单向量读取不足，还是原生生成能力需要任务适配。**
