1.3     VLM、VLA、规则与技能库各是什么
  VLM（视觉语言模型）接收视觉和语言信息，输出语言或可被程序解释的结构化内容。
本项目中的 Qwen3-VL 本体属于 VLM。
  VLM 驱动的技能调用系统把这个模型接到预定义动作接口。模型输出 move_forward
等技能名和参数，执行器再调用底层策略。动作不是模型输出一串自然语言后随意解释，而
是按固定接口严格解析。
  分层视觉语言动作策略可以用来描述经过动作示范训练、从视觉和语言预测技能的整
套系统。是否称为“分层 VLA”取决于使用的术语习惯；关键是写清楚动作层级。本项目
输出的是技能层动作，不是每个电机关节的目标角度或力矩。
  规则老师用明确程序逻辑生成下一技能。它不通过梯度更新学习，但可以产生训练示
范。技能库则给出了动作名称、执行接口、约束和已有控制器。它不是一段“让模型想象
鸭子如何运动”的文字。

“固定技能”不等于“固定整段任务”
  左脚踢球的底层动作已经训练好；但是走向哪个球、什么时候转身、如何接近、何时
  踢球，仍可根据每次新画面改变。你需要学习的主要是这些技能之间的选择与切换。

1.4     训练、推理和物理控制是三个不同的时钟
  训练中的一次更新，在当前机器上约需 22 秒，处理四条已经保存的样本。此时不要求
真实机器人同步运动，主要工作是计算损失和梯度。
   推理中的一次决策，消耗的是看当前图像并生成输出的时间。它可能随着模型、后端、
输入长度和显卡状态改变。训练一次更新的 22 秒不能直接当作部署时一次技能决策的延
迟。
   底层控制以较高频率读取身体状态并给出关节动作。当前策略控制约 50Hz、物理仿真
步频 200Hz。上层模型等待时仍须维持站立；不能等每个语言 token 出来才给电机一次指
令。

2.3     从一张图片到一句回答

2.3.1    第一步：把人类输入整理为消息
    人类看到的是“这张图里有什么？”和一张图片。程序看到的是一组有角色的消息：
system 给出任务约定，user 提供图像和问题，assistant 是模型要生成的回答。一个用户
消息可以包含多个图像块和文本块。Processor 负责聊天模板、文字分词和图像预处理。[5]
    下面是教学用伪结构，帮助理解数据方向，并不是复制即可运行的模型调用代码：

 messages = [
   {role: "system", content: [task_and_output_rules]},
   {role: "user", content: [front_rgb, near_rgb, instruction, state]}
 ]
 processed = processor(messages)
 answer_tokens = model.generate(processed)
 answer_text = tokenizer.decode(answer_tokens)



  训练时还会附加已知的正确 assistant 回答；推理时只给到 assistant 应该开始回答的位
置。两者输入格式要对齐，否则模型训练时见到的分布与实际执行时不同。


2.3.2    第二步：图片变成视觉特征
  模型并不是先把图片完整地翻译为一句中文再思考。它会把像素整理为小块，让视觉
编码器计算一组数值向量。例如，一个向量可能携带局部颜色、边缘、纹理与物体关系等
混合信息；不能把每个维度都直接解释成一个人类概念。
  Qwen3-VL 的主要组成是视觉编码器、视觉与语言之间的合并／投影模块以及语言模
型。系列报告说明，2B 和 4B 使用 SigLIP2-Large 作为视觉编码器基础；视觉特征经空间合
并后进入语言模型。[2] 合并与投影的作用，可以理解为把视觉侧的数值表示变成语言侧能
利用的表示。维度匹配只是必要条件，跨模态训练还要让这些表示具有可用的对应关系。
 “视觉 token”与“文字 token”不能混为一谈。文字 token 有词表编号，可以解码为文
字片段；视觉 token 通常是从图片计算出的向量序列。二者在多模态上下文中相互作用，并
不表示每块图片都必定对应某个汉字。
     Qwen3-VL 还通过 DeepStack 将不同深度的视觉特征融入语言层，使用交错式 MRoPE
表达空间／时间位置，并通过文字时间戳处理视频时间关系。这些是模型家族的结构能力。
[3] 当前小鸭子每次提交的是两张观察图片，不能因为基础模型支持视频，就把当前管线说
成已经输入连续视频。

常是三通道颜色值；隐藏状态是一组浮点向量；最终输出则是可以解码为文字的词表编号。

2.3.4    第四步：逐个生成输出 token
  语言模型根据当前全部输入以及已经生成的回答前缀，计算下一个 token 的分数，归一
化后得到概率分布。选择一个 token、接到回答后面，再继续下一次预测，直到结束标记或
达到生成长度限制。官方推理接口最终把生成的编号解码为文本。[6]
    如果回答是“前面有一个红球”     ，模型并不是从固定句子表里一次挑中整句；如果回答
是 JSON，它同样要逐段生成括号、键名、值和标点。一个动作名称可能由多个 token 组成，
不能假设 move_forward 必定只占一个 token。

2.4.1    用一个简化样本理解学习过程

2.5     Instruct 是怎样在预训练后形成的
  系列技术报告的后训练流程包含监督微调（SFT）、强模型到弱模型的知识蒸馏以及强
化学习（RL）；标准回复与显式推理格式的数据面向不同版本。[2] 这些概念分别解决不同
问题：

  • SFT：学习示范。给定问题和目标回答，用目标回答监督模型。你当前的机器人训练也
    采用这一基本形式，只是示范来自任务规则和仿真记录。
  • 蒸馏：学习更强教师的行为。教师可以提供答案或概率信息，学生学习模仿其中有用
    的能力。教师是规则程序时，通常更直接称为示范模仿；不应自动宣称使用了厂商相
    同的蒸馏算法。
  • RL：依据奖励改变策略。训练中生成候选行为，依据可验证结果或其他奖励信号优化。
    保存失败案例本身不是 RL；必须把奖励与参数更新过程实际连接起来。

  厂商用过 RL，不意味着我们现在也在跑 RL；我们接着一个经历过多阶段训练的基础
模型，用自己的监督样本进行 QLoRA。SFT 描述学习信号，QLoRA 描述参数更新与存储
方式，两者可以同时成立。


2.6     它的输出格式究竟由谁决定
  基础模型的自然输出是文本 token 序列，没有天生绑定我们五字段的机器人 JSON。固
定格式来自几层约束的共同作用：

 1. 系统提示告诉模型可用技能、各参数的意义，以及只能生成什么格式。
 2. 微调样本反复示范相同格式和合理决策，使输出更符合任务。
 3. 解码约束（如果实际启用）限制可生成的语法结构；本次不能把“提示要求 JSON”自
    动说成实现了强制语法解码。

没有把“发出踢球命令”自动当成“踢球成功”   。全文中的采集数量与样本均取自已经冻结

3.1   仿真里的小鸭子与三个球
  场景由 scene.py 读取本地 Microduck 的 scene_ball.xml 后生成。机器人有可移动、可
转动的自由基座，躯干主体名为 trunk_base。底层策略控制 14 个关节：每条腿各有髋偏
航、髋侧摆、髋俯仰、膝、踝，共 10 个；颈俯仰及头部俯仰、偏航、侧摆，共 4 个。嘴部
不在当前 14 维控制输出中，所以这轮技能训练并没有实现“张嘴叫两声”或“叼布”。
     动力学使用 CPU MuJoCo；load_scene(...,"hd1910") 加载本地 HD1910 参数文件
1910_m6.json，通过 BAM 执行器模型把关节目标变成力矩。记录中的 actuator=sts3215
是这套模拟实现的模型名称，不能据此认定实体机器人的实际舵机型号。当前名义配置为
5 ms 物理步长、4 个物理步的命令延迟，即 20 ms；电压、压降和延迟固定，不进行这部分
的域随机化。它也不是原先 GPU/Warp 训练环境的逐位复现。
  红、黄、蓝三个球都能在物理世界中运动、碰撞；球半径为 0.035 m，场景为灰色棋盘
地面。主集合随机抽取距离 0.3–0.6 m、方位覆盖一整圈的位置，球之间至少相隔 0.20 m。这
里先均匀采样半径、再均匀采样角度，并非在圆环面积上均匀采样。复位时机器人躯干初
始高度 0.12 m，关节置于已有策略的 HOME 姿态，先执行 2 s 站立，再开始任务记录。
   球的位置、相机和接触都由同一个物理场景产生；踢球效果不是播放一段角色动画，也
不是直接修改球坐标来假装踢中。实际关节目标、接触力、球运动与身体倾斜都有轨迹记
录。

3.4.1    成功和失败怎样确认
      踢球验收独立读取物理真值：要求指定脚在踢球开始后 0.54 s 的窗口内碰到指定球，目
标水平位移至少 0.12 m，无机器人碰其他色球、无踢前提前碰目标球；全过程倾角小于 30◦ 、
躯干不低于 0.065 m。最后还须站立，倾角小于 10◦ 、平面速度小于 0.025 m/s、角速度小于
0.3 rad/s、躯干高度大于 0.09 m。程序还检查轨迹和数值有效性。
  这些结果是“规则老师在这批仿真里的验收结果”
                       ，不是预训练或微调 VLM 的成功率。
近场任务已经把目标放在脚边，也不能与随机远近、可能需要转身寻找的任务混在一起报
告一个令人误解的成功率。
  23 个随机踢球失败任务中，9 个是验收未通过、12 个搜索未找到、2 个超时。原始图
像、动作与失败原因全部保留；正式 SFT 排除这 23 个任务的全部动作和结束标签。不过它
们所在 episode 各有两次独立成功的视野问答，这 46 个问答任务仍可保留。直接动作另检
查身体稳定、无球接触以及实际位移／偏航方向，不能只检查文字解析正确。

  这套系统把“理解画面与指令，选择下一步”和“让关节持续运动并保持平衡”放在不

4.1     还没有机器人微调时，模型为什么知道技能库
  模型并不会自动扫描本机目录，也不会仅凭“你是一只小鸭子”知道有哪些动作。应
用程序每次发送完整的 SYSTEM_PROMPT，其中明确列出九个技能、机身坐标、方向含义、持
续时间范围、两台相机的用途、脚边目标点以及回复格式。它还包含“走一步后结束”       “看
不见目标先转身寻找”等接口示例。这是人写的使用说明，属于推理时上下文；没有因发
送提示词而更新模型权重。
  预训练的指令模型已有读取图像和语言、遵循指令、生成文本的基础，因此可以尝试
在这个说明下选择技能。它是否选得正确、能否持续执行完整任务，仍需测试。微调则把
大量“本机画面＋原指令＋必要状态和历史 → 正确技能及参数”变成训练监督，让权重更
适应这套机器人和任务。
  因此至少要区分三层“已经训练”：Qwen 的通用预训练／指令训练、已有 ONNX 动作
策略的训练、本次机器人技能调用的微调。代码里的 is_trained_vlm=True 只说明正在调
用一个有预训练权重的模型；同处的 robot_finetuned=False 明确没有加载本项目微调结
果。不能把前者读成“本机微调已经完成”。


4.1.1   目标颜色究竟从哪里来
  以“别踢蓝球，把红球踢出去”为例，原话直接进入 user 输入。模型需要理解要操作
的是红球，再从双图和辅助检测寻找对应目标；当前技能层不调用规则解析器先替它决定
红色。提示词只告诉它合法颜色值有 red、yellow、blue，没有替当前指令填写答案。
    模型输出的 target_color 是它本次声明的目标，不保证一定理解正确。guard 检查的
是这个声明颜色的球是否可见、是否在脚边，不能代替语言理解。如果模型把红球任务说
成蓝球，而蓝球又恰好符合脚边条件，仅通过 guard 也不等于完成用户任务；独立测试的
expected_color 才会按预先指定的目标验收。该测试参数不送给模型。
  历史 selected_color 可以来自以前实际选择过的任务；用户当前明确指定另一颜色
时应以新指令为准。普通前进、后退和问答的 target_color 应为 null，不能因为场景里有
红球就擅自生成红球任务。

4.3     一轮真实运行经过哪些部件
 1. 观察。取得当前双图和测量状态，构造 SkillInput，四项内容为 instruction、images、
    state、context。保留原话及最近六条动作／反馈；去除任务编号，使用任务内相对
    时间。
 2. 请求模型。LocalVLMBackend 把 RGB 编成 PNG，
                                     再作为图像内容发送到本机回环 HTTP
    服务。消息含 system 与 user，温度为 0，最多生成 256 tokens，并请求严格 JSON schema；
    模型别名是 microduck-vlm。
 3. 解析与新观测检查。先严格解析 JSON，再取得更新的观测做 guard。模型推理需要时
    间，初始图片不能直接被当作执行瞬间的状态。
 4. 执行或拒绝。guard 通过才调用 Runtime.execute。拒绝时不偷偷替换成规则动作，而
    把拒绝原因留给下一次模型决策。连续三次拒绝则结束任务。
 5. 底层控制。对应 ONNX 读取本体状态并连续输出关节目标，MuJoCo 推进物理。记录
    实际开始、结束以及 completed 状态。
 6. 恢复、反馈、再看。非站立动作自动恢复站立，普通动作 1 s、踢球 3 s；然后重新观察，
    把本次提议及实际反馈放进 history，继续同一语言任务。

  guard 对动作要求机身倾角不超过 25◦ ；踢球还要求身体静止、指定颜色在当前 RGB-D
测量中存在，以及球心落在对应脚目标点的双轴 ±0.012 m 区域内。它只作接受或拒绝，不
替模型决定该左移还是右移。其目标也不是覆盖全部导航危险：它没有把普通移动自动变
成避障规划；相关选择仍由模型负责。
  上一条记录即使叫 previous_action，也要结合 previous_feedback 理解。部署时其
中可能保存被拒绝的提议，不能因为历史里出现过 kick 就认为真的踢了；只有成功执行反
馈才能证明执行。当前成功示范主要提供 executed_and_recovered 反馈，不能宣称已经充
分训练了所有拒绝后的恢复行为。
  推理超时、格式错误或服务异常会留下日志并结束当前任务；程序没有静默回退到规
则老师。停止请求有独立通道，推理在后台线程等待时仍可取消；被取消或超时请求的迟
到回复不会再进入动作执行器。


4.4     50 Hz、200 Hz 和 VLM 推理不是一个频率
    MuJoCo 每 0.005 s 走一步，执行器 controller 也在每步更新，因此是 200 Hz。技能策略
每 0.02 s 计算一次 ONNX 输出，即 50 Hz；随后四个物理步使用该周期的目标。模型选择一
次 0.5 s 踢球技能，意味着底层约运行 25 次 ONNX 推理、100 个物理步，不是 VLM 需要输
出 100 次关节命令。

5.3     为什么训练时把正确答案也放进输入
  这是自回归监督训练的 teacher forcing。假设目标 JSON 被分词为 y1 , y2 , . . . , yT ，训练
时同时提供完整序列，但通过因果注意力约束，预测 yt 时只能看到原始输入和 y1 , . . . , yt−1 ，
不能看到当前位置和未来的正确 token。
  例如模型预测 move_right 时，允许使用前面已经给定的 JSON 键名；它不能直接读取
正在预测的答案。对第一枚助手 token，则使用输入末尾位置产生的 logits。推理时没有正
确答案可供拼接，模型要逐个使用自己已生成的 token，因此训练损失下降与自由生成正确
率并不等价。
    本地实现采用显式因果移位。设输入长度为 P ，完整长度为 L，取预测位置 P − 1 至
L − 2，对应标签位置 P 至 L − 1。本例 P = 2642, L = 2683，所以预测位置为 2641 至 2681，
标签位置为 2642 至 2682，共 41 个。
    logits_to_keep 只要求词表输出层计算这些位置，得到约 [1, 41, 151936] 的 logits。它
没有删掉前面 2642 个输入 token 的注意力上下文。若在所有位置都构建词表 logits，中间
张量会大得多；这是本次能在小显存上运行的一个关键实现选择。

占用约 5300 MiB（5.2 GiB）
                    。allocated 是活跃张量使用量，reserved 还包含 PyTorch 缓存池，
整卡统计另含 CUDA 上下文、桌面显示和其他驱动开销。不能用整卡占用直接推算“模型

6.1     先分清两个维度
  “用什么误差教模型”和“允许哪些参数改变”是两个独立选择。SFT、偏好学习、强化
学习描述学习目标和反馈形式；训练分类头、LoRA、QLoRA、局部解冻、全量更新描述参
数与存储方式。不能把它们排成互相替代的一列。例如当前方案同时属于 SFT 和 QLoRA；
DPO 也可以只更新 LoRA，而不必更新全部底座。
  另一条独立维度是输出形式：可以生成 JSON 文本，可以直接输出技能分类概率，也
可以预测连续动作。它们不由“使用 VLM”这三个字自动决定。小鸭子已有可靠的底层技
能时，首先要学的是根据观察选择技能、参数和结束时机；是否训练关节控制器是另一项

6.2     方案一：冻结 VLM，只训练技能预测头
  这通常是一个很值得做的对照实验。先让冻结的 VLM 将允许输入变成向量，再让一个
小网络学习如何将这个向量映射到技能。冻结特征后训练新层、或预先保存特征再训练小
模型，是标准迁移学习流程；官方 Keras 指南也明确说明了缓存能减少重复骨干计算，以及
动态数据增强会使固定缓存不再适用。[10]


6.2.1    必须缓存联合输入特征，不能偷看目标
    对于第 i 条样本，先构造：

                      zi = Fθ0 (Iifront , Iinear , ui , si , hi ),   θ0 保持冻结.

这里 ui 为用户指令，si 为允许状态，hi 为历史。对于因果 VLM，一种候选读出位置是助
手开始标记之前或完整输入末端的隐藏状态，它已能注意到前面的图像、指令和状态；也
可以比较输入位置池化。究竟哪种读出更适合技能预测需要验证，不应把“最后一个向量”
当成已证明的最佳表示。
  缓存时绝不能将目标 JSON 接在后面，再从回答末端取向量。那样特征已经读到了正
确技能，训练和离线测试可能看起来极好，上线时却拿不到这样的特征。教师动作、规则
阶段、仿真世界坐标、任务编号、文件名中的标签也不能偷偷混进输入。相同画面配“踢
红球”和“踢蓝球”时，联合特征应允许因指令不同而不同；只缓存图像向量后直接分类，
会丢掉语言条件。
   缓存还应固定底座版本、提示词、处理器、取特征位置和推理模式，并为缓存记录输
入与配置哈希。图像或文字增强改变了输入，就应重新提取对应特征；一旦开始更新骨干
或 LoRA，旧联合特征也会失效。数据的 train、val、test 划分必须在特征训练前固定，标准
化统计只从训练部分估计。

seconds=0；移动时长只能为 0.02 至 0.60 秒，站立和转向为 0.02 至 1.00 秒；两种踢球固定
0.50 秒。可以先选择 type，再在对应合法技能与时长集合中解码。训练 duration 项也使用
正确技能对应的合法集合，推理则必须使用预测技能，不能继续用真值来替模型纠错。
    颜色不能简单规定“非动作一律 null”。本地示范中，完成踢红球任务的 finish 仍可保
留 red；而回答视野问题通常为 null。哪些结构组合不合法可由接口确定，但“这次应该选
蓝色还是红色”是需要学习的内容，不能用测试标签建立屏蔽表。

                      Lhead = λt CE(atype , t) + ms λs CE(askill , k)
                                + md λd CE(aduration , d) + λc CE(acolor , c).

其中 ms 只在 type 为 skill 时取 1；md 只在需要学习可变时长的动作上取 1。固定踢球时长
可直接由接口赋值，避免训练一个没有选择余地的分类项。各权重可先设为 1，再依据验证
集调整，不能为了提高测试分数反复改测试配置。若少数技能严重不足，可以在训练集内
采用类别权重或分层采样，同时保持评估分布清楚可追溯。
  例如“向前一点”的正确标签可以为 skill、move_forward、0.32、null。若模型把类型
判成 finish，即使另一个头恰好选对 move_forward，最后动作仍然错。评估必须查看联合结
果，而不只是分别挑最好看的单头准确率。分类概率也不天然是可信置信度；若使用低置
信度转为 clarify，需要在验证集上校准并检查是否滥用澄清来逃避任务。

6.2.3    技能头怎样保留“你看到了什么”
  分类头只输出有限类别和参数，不能凭空生成自由中文 reply。一种完整部署方案是：
动作、结束和固定澄清由头决定并填充模板；当 type 为 answer 时，再调用冻结 VLM 的文
本生成能力回答当前画面。另一种方案是另训练回复解码路径，但那已超出“只训练小分
类头”。
  因此比较两种方案时，应分别测动作决策和视觉问答。不能把只会输出 skill ID 的小头
称为已经拥有完整对话功能，也不能假定冻结底座的回答在新的仿真视角上一定正确。无
论哪种输出方式，最终都要转换为同一个技能协议，再经过相同的时长约束、踢球条件和
执行反馈闭环。


6.3     其他参数更新方法何时有意义

6.3.1    投影器或局部解冻
  当图像特征对新相机外观、视角或任务细节不够适配时，可以研究更新视觉到语言的
投影模块、语言末端若干层，或小部分视觉层。它比全冻结有更多调整空间，但“解冻一小
块”并不自动意味着显存很小：只要梯度要穿过相关路径，就需要保存或重算激活。当前
视觉编码器和投影器全部冻结，尚无这一方案的本机性能结论。
  应先检查错误来自哪里。若颜色识别已对，错误集中在何时停止，先改善上层示范和
时序监督通常比改视觉模块更直接。若目标在图中只有几个像素，换训练参数也未必能弥
补输入分辨率缺失；需要一起评估图像设置、相机覆盖和数据质量。


6.3.2    LoRA、QLoRA 与全量 SFT
  LoRA 用低秩矩阵表达权重变化，QLoRA 则把它与量化冻结底座结合。选择 r 是容量
与成本的权衡，不是准确率旋钮；更大 r 需要更多可训练参数，也可能更容易记住有限示
范。本次 r = 8 是经过显存验证的起点，不代表已经搜索过全部最优配置。[7, 8]
    全量 SFT 允许原模型大量参数直接更新，适应空间更大，但也需要存放更多梯度与优
化器状态，且可能损伤原有视觉语言能力。“全量微调”仍然从预训练权重出发，和随机
初始化后从零训练不同。现有 6 GB 环境没有验证全量方案；不能直接套用当前 QLoRA 的
15–17 小时估算。
  如果冻结特征小头明显欠拟合、数据质量可靠，再考虑增大头、训练部分适配器或局
部解冻，可以更清楚地识别新增复杂度是否有效。每改变一次可训练范围，都应单独记录
数据、参数量、资源和评测结果，而不是同时改变所有设置后把改进归因于某一个名词。

6.4     偏好学习和强化学习不是“更高级的微调按钮”
  DPO 使用同一输入下的偏好输出对，促使模型提高更好输出相对于更差输出的倾向。
它需要明确的 chosen/rejected 数据，方法本身不等于让机器人在线探索。原论文将其作为不
必显式训练奖励模型的偏好优化方式。[11]
  对小鸭子，可以研究“目标偏左时，小幅左转”优于“直接踢球”的偏好，但不能仅因
某个输出来自现有规则就自动认为它永远更好。有效偏好应结合执行结果、对齐程度和任
务完成情况。当前数据主要是输入到单一教师动作，尚没有经过验证的偏好对或 DPO 训练
代码。
  强化学习则让策略通过环境交互，优化整个轨迹的累计奖励，例如正确球被踢动的奖
励、错误球接触的惩罚、跌倒或超时惩罚。奖励和终止条件定义不好，策略可能找到“看起
来得分但任务没完成”的行为。语言模型领域的 RLHF 展示了示范、偏好与后续强化优化
可以组合，但这不直接证明同一流程能迁移到本机器人。[12]
  还需区分层级：训练上层“选择左转还是踢球”的策略，可以继续复用底层控制器；训
练底层步态或踢腿，是另一套状态、动作频率和奖励。本次上层 QLoRA 只模仿示范，没有
在线奖励优化，也不会在每次日常执行动作后自动再训练一轮。


6.5     怎样公平比较小头与当前 JSON 方案
  比较应使用相同的训练、验证、测试划分和独立场景种子，输入相同两幅图、同一指
令及允许状态，采用同样的技能库与执行器。两种方法可以选不同输出表示，但不能给一
方额外的目标坐标或未来反馈。任何特征缓存都只能由该条允许输入产生。
  离线部分至少报告合法输出比例、动作样本上的九技能准确率和混淆矩阵、每种颜色
准确率、时长误差与精确一致率、四字段联合准确率，以及视觉回答是否符合图像。分类
头天然容易保证结构合法，JSON 模型需要生成正确结构；应分别报告原始输出质量和进入
同一执行 guard 后的结果，避免比较口径不一致。
  闭环部分使用相同新场景和任务说法，测正确颜色球的实际踢动成功率、错误球动作、
搜索步数、耗时、失败与拒绝原因。还应测试目标最初在盲区、靠近时暂时出视野、执行被
拒绝后的调整，以及“往前一点”完成后能否停止。离线标签存在多种合理解时，精确匹
配低不一定说明任务差；反过来，离线匹配高也可能在连续执行中积累误差。
  成本比较要包括特征提取时间、后续训练时间、峰值显存、实时每次决策延迟和总实
验迭代成本。缓存方案不能只报小头训练几秒而省略首次 VLM 提取；当前 JSON 方案也不
能只报权重小而忽略逐 token 生成时间。测试集用于最终报告，不用于反复选择头大小、阈
值或提示词。
  截至本报告快照，已经具备的是可恢复的 QLoRA 训练、独立数据划分和初始离线基
线。冻结联合特征加多头分类器是一项清晰、可复用现有数据的后续对照方案；其收益必
须通过上述共同标准验证，不能先把它写成更快且更准的既定结论。

7.5     第三级：在仿真中从头完成任务
  离线评测给模型的是规则老师轨迹上的观测。部署时，模型自己的选择会改变下一幅
画面：少走一点、多转一点、提前踢一下，都会产生训练中较少见的状态。这种输入分布变
化，是行为克隆需要闭环验证的主要原因。
  完整踢球验收应从新的初始状态开始，给出明确颜色指令，允许模型搜索、靠近、对
齐、踢球，最后由独立程序读取真实接触和位移证据。需要同时报告：

 1. 目标是否找到，是否在看不到目标时错误声称目标不存在。
 2. 是否到达可踢位置，是否重复动作、来回振荡或过早结束。
 3. 是否选择正确颜色、正确脚，是否碰到非目标球。
 4. 踢前是否提前推球，踢球是否产生目标脚接触与足够位移。
 5. 是否恢复站稳，有无摔倒、超时、拒绝或决策次数耗尽。
 6. 总模型调用次数、每次推理耗时、总墙钟时间和仿真时间。

  近脚已对准任务和随机远距离任务必须分开。前者只需较少动作，后者包含搜索和长
期控制。把两类混合后得到较高成功率，可能掩盖导航能力不足。
  当前默认 VLM 上限是 40 次决策；采集的合格踢球示范中，有 40 个任务需要超过 40
次决策，最长 117 次。因此后续闭环对照应显式设为 --vlm-max-steps 120，并独立记录
每任务 600 秒墙钟上限。调整上限只保证任务有足够机会执行，不保证它会成功。

7.7     失败数据什么时候能够帮助学习
   当前保留了 23 个失败踢球任务的原始记录，但没有把它们作为正确动作监督。仅保存
“失败了”的标签，不会自动告诉模型哪一步应该改成什么动作。
  下一轮有三种不同处理方式。第一种是人工或可靠老师为失败状态补上正确的下一步
动作，形成新的 SFT 样本；第二种是构造同一输入下经过核验的较好和较差输出，用于偏
好学习；第三种是在可控仿真中定义奖励并训练策略。三者需要不同数据与训练目标，不
能把失败轨迹直接混入当前成功示范 JSON 损失中。
  对于这个项目，补充模型实际走偏后的状态尤其有价值。比如“红球仍在左侧，刚才
右转错误，下一步应当左转纠正”需要真实观测、允许的执行历史和经过验证的纠正动作。
纠正动作不能只根据最终失败倒推猜测，也不应把后续才知道的真实结果放回当前输入。


7.8     完成这一轮之后，怎样决定下一步
  先检查生成输出是否稳定合法、运动命令是否能执行一次后结束，再评估近脚踢球，最
后评估盲区搜索与随机远距离踢球。如果格式很好而搜索差，优先检查搜索数据与历史表
示；如果目标颜色常错，检查同一画面不同语言目标的数据覆盖；如果对齐时来回摆动，检
查距离特征、动作时长分布及规则老师隐藏锁脚状态。
  还应单独检查视野问答。当前监督主要描述球，不应把模型答出某些新物体名称视为
已验证能力。开放问答需要新的场景、多样物体及明确评价准则。模型训练完成这个文件
状态，只表示优化流程到达计划终点；是否适合接入日常交互，要由这些具体评测决定。

8.3      中途测试：当前已实现的是离线评测

环境，后者不能在训练期间当成闲置环境删除。检查点滚动保留策略已控制一部分磁盘增
长；不要在进程写入时手动移动或删除当前检查点目录。

9.1   我没有微调，VLM 为什么能输出技能名
  模型可以在本次输入里读到技能清单及少量示例，然后按这些名称生成文字。这叫利
用上下文执行指令，不需要当场更新权重。就像你给一个会读说明书的人一张按钮表，他
可能按照说明选择按钮；是否能在复杂状态下一直选对，还需要实际验证。
  本地微调把许多“这个输入应该选择这个技能”的对应关系用于更新参数，让模型更
适应这套任务。技能库本身由代码定义。未来新增技能时，需要增加可执行控制器、参数
约束、接口说明、示范和评测，不能只在提示词里多写一个不存在的动作名。


9.2   颜色、位置和正确动作分别从哪里来
  “踢红球”里的目标颜色来自用户原话；延续性任务还可利用允许的上下文。当前两路
RGB 和 RGB-D 辅助测量提供可见球颜色与相对位置。规则老师据此选择动作，导出器把
通过验收的选择写为目标标签。
  模型输入中不会直接放入本次正确的 skill。评测专用的 --expected-color 也不进入
模型输入。否则模型可能读取答案而不是理解目标，得到看似很高但无意义的分数。


9.3   JSON 格式是谁规定的，是否永远固定
  五字段格式由本项目的协议、提示词与解析器共同规定。Qwen 本身是可生成文本的模
型，不天然被限制为这五个字段。训练目标会强化这个格式；部署还应保留严格校验。改变
字段名、允许的技能或时长范围后，应同步改变提示词、训练标签、解析器、执行器和测试。
  当前离线生成评估不使用强制 JSON 语法解码，输出可能不合法。原有 GGUF 服务与
客户端的约束方式则应按实际请求记录识别。比较两个后端时，不能一方强制格式而另一
方无约束，却把全部差异归结为模型权重。


9.4   SFT、LoRA 和 QLoRA 是不是三种互斥训练
   它们描述不同维度。SFT 说的是“拿示范输入和正确输出做监督训练” ；LoRA 说的是
“只训练插入的小矩阵”；QLoRA 进一步说的是“以低比特量化基础模型，训练 LoRA”。因
 此本轮可以同时被称为 SFT、QLoRA；其中动作示范部分也属于行为克隆。
  同一个 SFT 目标，可以选择全量参数、部分层、LoRA 或冻结特征后的预测头。DPO
等则改变训练数据结构和目标，不能仅通过把优化器名字替换一下就变成另一种学习方法。

9.5     预测技能概率和生成技能 JSON 有什么不同
  技能预测头可以一次输出九个技能的分数，再通过 softmax 得到归一化概率；另设任务
类型、时长和颜色头，最后由程序组装 JSON。它的输出类别由头的维度和标签表规定。
  当前 QLoRA 方案逐 token 生成 JSON。它在每个生成位置对词表中的 token 分配概率，
经过多个 token 才形成 move_forward 及其他字段。两个方案都可以学习技能选择，但损失
形式、解码方式和格式错误类型不同。生成模型中的一个 token 概率，不能直接当成某个完
整技能的可靠成功概率。


9.6     动作是离散的，为什么还要预测时长
  技能名称是离散选择。前进 0.10 秒与前进 0.60 秒属于同一技能，但会造成不同位移和
下一幅画面。持续时间决定一次决策的幅度，也影响闭环频率。
  当前接口把时长限定为 0.02 秒的整数倍，转向和站立上限 1 秒，平移上限 0.6 秒，踢
球固定 0.5 秒。因此可以把时长看作受限制的参数，也可以在新预测头方案里离散成类别。
不能把“所有技能都离散”理解为每个技能永远只允许同一个执行时长。


9.7     为什么一次只执行一个技能
  当前画面可能只能证明“向左转一点合理”
                    ，不能保证转完后前进再踢球仍然合理。短
动作后再观察，使系统有机会纠正误差。一次生成整串动作会积累位置误差，还容易错过
球或误碰其它球。
  这不意味着模型每个物理步都要重新推理。一个短技能由底层控制器连续执行，上层
在技能完成并恢复站立后再获取新观测。上层和底层分工，兼顾语言决策与稳定运动。


9.8     训练是不是同时运行四只鸭子
  本轮不是在线与仿真交互的强化学习。数据采集阶段曾用三个独立仿真进程加快采集；
正式训练阶段从磁盘读取样本，一个 GPU 训练进程每次处理一条样本，累计四条的梯度后
更新一次。
  GPU 内部矩阵运算本来就有大规模并行，但这与同时放入几条样本、运行几个仿真环
境是不同层面的“并行” 。把梯度累计 4 改成 8，只改变累计多少样本后更新，不会自动把
读取和前反向变成八条同时处理。

9.9     为什么只训练少量参数，仍然要十多个小时
  参数更新数量只影响部分成本。图像编码、
                    长上下文语言主干前向、     用于训练各层 LoRA
的梯度传播、梯度检查点重算和量化计算，都仍需执行。batch 为 1 也限制了摊薄某些开销
的机会。
  冻结后缓存特征的方案能够将主干成本集中到首次特征提取，随后只训练小头，所以
后续训练通常更轻。但在线运行新图像时仍要计算特征，不能直接用“缓存后训练很快”推
断机器人每次决策同样很快。


9.10      冻结、eval 和 no_grad 分别是什么意思
  冻结参数通常表示不为这些参数计算或保存需要更新的梯度。eval 模式改变 dropout 等
模块的运行行为，使推理更稳定，并不自动禁止梯度。no_grad 表示该计算范围不建立用于
反向传播的梯度记录。
    训练 LoRA 时，基础权重虽冻结，相关层仍需参与使 LoRA 可学习的计算图；不能随
意把整个主干套进 no_grad，否则可能切断 LoRA 所需梯度。完全冻结特征提取器、只训练
外接头时，则可以把特征提取放在 no_grad 下。缓存特征时还应使用固定推理设置，避免
dropout 和输入处理不一致。


9.11      成功轨迹里也会有多余动作，怎么办
  最终任务通过，只能证明整段轨迹达成了验收条件，不证明每一步都是最优。老师可
能走了绕路或用了更多小调整。行为克隆会学习这些动作习惯，因此示范质量与覆盖率同
样重要。
  当前剔除了固定执行器恢复动作作为训练标签，但保留规则决策中的必要站稳。后续
可以对成功轨迹进一步审查、缩短冗余动作；同时要保留真实可执行和稳定性证据，不能
为了让轨迹更短而直接删除必要观察或站稳步骤。


9.12      为什么失败轨迹没有直接加进训练
  失败轨迹的某些早期动作可能合理，也可能已经偏离目标。当前没有可靠的逐步纠正
标注，因此保守地排除整个失败踢球任务的动作监督。这样避免把“最终失败的动作序列”
作为应该照做的答案。
  同一 episode 的独立视野问答可以是正确的，所以仍保留。将来若能给失败状态补上正
确动作，就可以把这些纠正后的样本加入训练；这与把失败轨迹原样当成正确标签是两种
操作。

9.13      有 RGB-D 辅助，还算 VLM 吗
   模型仍然接收图像和语言，并利用这些信息进行决策；增加结构化测量并不改变它采
用 VLM 的事实。但能力归因必须准确：当前球颜色分割和深度拟合由感知模块辅助，不能
把所有几何检测成绩都称为 VLM 从 RGB 独立学到的能力。
  若希望纯 RGB 决策，应设计单独的无检测输入实验，并重新检查距离判断、对齐和踢
球表现。把已经训练依赖测量的模型直接删掉测量字段，只能算分布变化测试，不能预先
保证性能相同。


9.14      是不是需要 VQ-VAE 动作码本
  当前九个技能已有明确编号和执行器，因此可以直接预测技能类别或生成技能名称，不
必再训练一个压缩连续动作轨迹的码本。VQ-VAE 等方法适合某些希望从复杂动作序列中
学习离散表示的方案，但不构成本项目技能分类的前置条件。


9.15      “看到了什么”的功能怎样保留
  当前 JSON 接口包含 answer 和自然语言 reply，训练数据里也有视野问答。QLoRA 能
够把这类问答纳入同一个生成目标；但已有示范主要围绕三色球，开放环境描述仍需单独
数据和评测。
  冻结 VLM 加技能头时，可以保留原 VLM 语言生成分支来回答问题，由任务类型判断
选择技能头还是语言回复。技能头自身只输出有限类别，不能独自生成任意场景描述。也
需要防止问答请求误触发运动。


9.16      自由表达是否需要每一句都写规则
  预训练语言能力可以让模型理解未逐字出现过的表达，但它能否把这些表达正确映射
到你的技能，需要验证。数据应包含同一意图的多种说法，也需要同一画面对应不同目标
和不同运动指令，避免模型只看图或记住固定任务顺序。
  目前采集包含多种预先设计的表达，并通过独立复位运动数据减轻顺序捷径。它不等
于已经覆盖所有口语、否定、组合任务或含糊指代。对“别踢红球，去踢蓝球”
                                  “先看看再
往后退”等复杂表达，必须明确是否属于支持范围再测试。


9.17      训练完是否还要 API，是否收费
    当前训练和推理使用本地权重，不要求云端大模型 API，因此没有这条流程产生的云
API 调用费；本地显卡、存储和电力仍有成本。官方模型卡声明 Apache-2.0 许可，使用时
应按实际许可证要求处理。[1]

A.5     从一个新实验到可比较结论的检查顺序
 1. 写清任务、技能接口、允许输入、成功条件及不支持的行为。
 2. 在采集前固定场景种子与训练/验证/测试归属。
 3. 保存原始观测、实际执行和独立物理验收，保留失败记录。
 4. 筛选示范，排除答案泄漏和未来信息，检查语言是否真的改变动作。
 5. 记录模型、提示词、数据与代码版本，完成最长输入资源试跑。
 6. 运行训练，保存基线、更新指标、恢复状态和异常。
 7. 用验证数据比较参数设置，用保留测试场景做最终报告。
 8. 将选定权重接入真实推理路径，验证输入输出一致，再进行闭环任务。
 9. 按失败类型补数据或改系统，另开版本，保留上一轮的可复现对照。

实际文件是否一致。报告生成只读取训练数据与状态，并未为制作 PDF 而暂停训练、切换
模型或重新采集。
