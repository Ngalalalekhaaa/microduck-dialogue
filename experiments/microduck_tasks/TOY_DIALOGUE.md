## 原生桌面交互入口

在当前电脑的桌面会话中，从仓库根目录运行：

```bash
.cache/microduck_head/venv/bin/python -m experiments.microduck_tasks.toy_desktop
```

程序打开 MuJoCo 默认原生窗口，并在右侧放置灰色中文聊天框，无需浏览器或 HTML 页面。聊天框由系统 `/usr/bin/python3` 的现有 PyQt5 运行；模型和仿真仍使用上述项目环境。记录默认保存到 `outputs/toy_desktop_<时间戳>/`。`--backend teacher` 仅供规则调试，不代表 Q1 输出。

默认加载真实 Q1 checkpoint100 生成 `decision + goals`，中文 `reply` 使用宿主模板，不能当作模型自由聊天输出。
Q1 的 P6 输入只有文本和结构化状态，不接收原始 RGB 图片；默认控制使用旧 RGB-D 执行桥，尚未切换到新增 RGB＋ToF 支路。本次修复交互和执行桥，没有重新训练或改写旧实验成绩。

动作按 1 倍时间逐帧显示，推理时仍冻结物理时间。聊天框区分计划接收与真实执行结果，完成／失败消息依据执行器验收。当前最多15个未完成目标，超限整组拒绝；安全暂停等待完整有限动作结束并站稳，保留剩余任务，持续行走则在短段边界站稳后保留同一目标；“继续”不重演已完成动作。停止／取消立即锁存信号、撤销当前任务并清空队列，迟到推理和停止前排队的旧指令不能重新启动任务。

此前“看不到动作”有两个原因：锁步执行快速推进，显示线程又受同一世界锁阻塞，只看到动作前后状态；软件渲染每次取图约0.49秒，还被踢球桥误判为超过0.3秒的观测期限，导致搜索动作根本没有执行。现在逐控制帧发布画面并按1倍时间推进，观测期限按图像时间戳与当前仿真时间的差值检查，仍保留0.3秒阈值。程序检测到 NVIDIA EGL vendor 后自动使用它并取消软件渲染强制项，无需手动设置；本机双相机 RGB-D＋检测中位耗时由486毫秒降至11毫秒。

修复后的同场景 CPU 复现中，“前滚翻→踢蓝球”均通过真实执行验收：右脚接触目标、蓝球移动3.07米、无提前推球或误碰其他球，并恢复站稳。报告为 `outputs/plan_guard_replay_20261116/reproduction.json`；这是一例执行桥回归，未调用 Q1，不代表任意指令或场景100%成功。

旧 `python -m experiments.microduck_tasks.toy_web` 仍作为可选浏览器调试入口保留，服务运行时访问 `http://127.0.0.1:8765/`；日常交互使用上面的原生桌面入口。

## 将规则教师移植为模型提示的实测

规则教师本身已经接收结构化输入，输出 `schema_version + reply + decision + goals`。
新增的 `--vlm-context rules` 测试另一件事：把教师的静态决策说明提供给原始 Qwen3.5-2B，
让模型自己生成回复和计划。规则说明在 `toy_vlm_prompt_rules.py`，包含13种自身动作的全部85个别名、
路由优先级、次数与角度、逐步目标绑定、历史指代、追加/替换/暂停/恢复、姿态前提、观察条件和完整 JSON Schema。
这不是运行教师解析代码；静态自然语言说明不能保证神经网络逐条执行规则。

每轮仍保留完整公开上下文和两张图。系统提示4029 tokens，本次32条诊断的完整输入4705～4804 tokens，
均未截断。没有给模型当前请求的教师答案，没有用教师修正模型输出，没有进行本任务微调。
明确停止/暂停及可信执行反馈仍走本地控制；找球、接近、踢球等底层闭环仍由既有执行器完成。

先冻结32条新的语言/状态诊断，再用相同图片和输入分别运行旧 `compact` 与 `rules`。
其中30条调用实际模型，2条停止/暂停由宿主处理，不计入模型成绩：

| 指标 | compact | rules |
|---|---:|---:|
| 模型输出通过格式及当前状态校验 | 21/30 | 26/30 |
| 模型计划合法且符合预设意图 | 10/30 | 11/30 |
| 合法模型计划与规则教师完全相同 | 6/30 | 10/30 |

这些诊断复用一对真实记录图像；部分姿态、队列、历史是标明的假设状态，不是32次物理执行。
它们测的是产品意图，不能当成逐字模仿教师的金标：审阅发现5例与教师保守规则存在政策差异，
包括坐姿下是否自动补站起、否定时聊天或澄清，以及“刚才”被教师当成过去叙述。
另有10例暴露教师对自然改写或参数的解析缺口。因此规则采集的高成功率只适用于已覆盖的话术和场景。
排除上述5例后的模型意图成绩仍只有 compact 9/25、rules 10/25；这是事后诊断分组。

另用原14项 MuJoCo 回归测试运行 `rules`，包含17次模型推理及2次宿主控制。
模型原始计划严格匹配为6/17，协议有效14/17；九个有限任务按原严格标准通过1/9，旧compact为2/9。
严格分数有表示差异：rules 的“踢蓝球→踢红球→左转360度”确实三步完成并验收，
但模型绑定了正确可见实体ID，标签为null，所以没有计入原严格分数。
补充语义执行审计保留原报告，只允许唯一实体绑定、属性顺序和未指定方向的整圈转向等价，
同时要求实际执行目标等于提交目标，且每步成功并通过验收；详见本轮 `semantic_execution_audit.json`。
按此补充标准，rules、旧compact、旧full均为2/9；rules完成前滚翻和蓝球→红球→整圈，
compact完成左转90度→前进0.6秒及前滚翻。rules的单目标为1/3、多目标为1/6，持续任务对话控制0/1。
补充审计没有放宽漏步、错颜色、错误角度或把坐下/站起合成另一种表演，不能据此宣称整体效果提升。

人工另审查两版全部64条回复。rules 仍会口头答应点头却输出 `respond + goals=[]`，
六步计划正确却提前称“已执行”，以及把满队列的追加写成 `replace`。
视觉回复错误称近场图也有蓝球；该图只有黄球局部，没有可见蓝球。计划得分不能代替回复或视觉事实得分。
本轮只改善了部分协议遵从，没有实现规则教师的等价替代，暂不能替代当前的规则采集器。

## 原始 VLM 的固定 JSON 试跑

可直接让本机的 Qwen3.5-2B 生成回复和任务计划，无需加载已训练的技能头：

```bash
./experiments/microduck_tasks/toy.sh --backend vlm --vlm-context compact --interactive
```

或用 `--command` 连续给几条指令。`--backend teacher` 是原规则采集器，`--backend selector` 是已训练小头；
三者的记录来源明确区分。VLM 试跑记录为 `training_ready=false`，不会自动混入教师 SFT 数据。

输入包括两路真实相机、用户当前原话、公开对话历史、身份、身体与环境状态、可见实体、
当前任务和待执行队列、已发生的执行结果以及本轮可用技能。完整输出合同固定为
`schema_version + reply + decision + goals`。技能字典覆盖13种自身动作，以及踢球、接近、移动、转向和姿态；
提示同时说明聊天/看图不改变任务、能力问句与动作请求的区别、坐姿前提、连续移动和队列控制。

`full` 上下文在 `toy_vlm_prompt.py`，包含完整 JSON Schema 和单目标字段示例。
`compact` 在 `toy_vlm_prompt_compact.py`，使用明确决策步骤、四个完整回复示例，并在输入末尾再次突出当前原话。
二者均保留完整任务上下文；compact 是组织方式调整，系统提示长度仍约2400 tokens。
后者是带上下文示例的无微调方案，不应称作严格的零样本测试。两个版本独立保存，不改动原训练特征合同。

生成使用原模型词表输出层、NF4量化、两路图像和新鲜缓存，单请求不补齐、不静默截断；
输入上限8192 tokens、输出上限768 tokens、生成时间限制90秒。提示要求JSON，生成后再严格解析并做上下文检查；
目前没有语法约束解码。重复键、非法数值、额外文字、非法技能和不满足执行条件的计划均拒绝；
保留原文和拒绝原因，不用规则教师修正模型的技能选择。达到生成限制但已形成完整合法JSON时仍可接受，原因写入记录。

用户回复与计划来自VLM；明确停止/暂停走本地控制，动作完成反馈依据执行器验收生成。
上述实测采用锁步仿真：推理期间暂停物理推进。当前宿主可以在推理期间锁存停止信号并拒绝迟到计划；安全暂停则保留推理及计划。两者都不能据此声称已实现边运动边推理或真机桌面控制。
计划正确率与聊天、视觉事实正确性分开检查，能生成合法JSON不代表选对任务或描述正确。

本轮实测在同一组14个仿真案例、19条用户消息上进行，其中17次模型推理、2次宿主停止/暂停：

| 配置 | 模型原始决策及全部目标严格匹配 | 完整有限任务计划正确且执行通过 | 平均模型响应 |
|---|---:|---:|---:|
| 首版冻结VLM + 已训练小头 | 8/17 | 0/9 | 3.33秒 |
| 原始VLM + full上下文 | 6/17 | 1/9 | 8.97秒 |
| 原始VLM + compact上下文 | 6/17 | 2/9 | 8.02秒 |

两版生成均有17/17条可解析为JSON，但只有10/17条通过完整协议和当前状态校验。
compact通过的完整有限任务是“左转90度再前进0.6秒”和前滚翻；连续行走中的聊天、暂停、恢复整段未通过。
它仍会漏掉点头、把转一圈写成30度，甚至把后空翻映射成前滚翻。错误计划中的单个动作也可能通过执行验收，
因此不能把已执行动作的成功率当作用户任务成功率。

额外20条预先固定的语言/状态诊断覆盖全部自身动作及多种组合：14/20条协议合法，
7/20条计划严格匹配；允许唯一可见实体ID等价绑定后，8/20条模型计划合法且语义符合预期。
该诊断只复用记录图像，不执行物理运动；姿态、桌面和队列部分为明确标注的反事实状态。
这些指标不评判回复事实正确性。full版视觉回复存在臆测球颜色与方向的问题；compact版两条简单红球回答有证据，
但额外诊断又把仅前方相机可见的蓝球说成两路都可见。其他对话仍会承诺没有提交的动作，
不能据此认为聊天和视觉问答已经可靠。

报告分别位于 `outputs/toy_vlm_eval_20261115/report.json`、
`outputs/toy_vlm_compact_eval_20261115/report.json` 和 `outputs/toy_vlm_language_20261115/report.json`，
视觉与回复人工审查另存同目录 `reply_audit.json`。compact设计参考了初版错误，14项是开发回归，
不能包装成未见测试；20项独立编写后固定，仍只是小规模诊断。
此次实验反映本机NF4量化、非思考模式和当前上下文配置的效果，不代表所有模型或量化配置的能力上限。
相关2668项实验回归测试通过，57个相关Python文件Ruff检查与格式检查通过。

另外核对了权重、处理器与分词器来源，11份下载元数据均对应固定revision，内容校验未发现版本混用。
同一“点头”输入的缓存生成重复两次，43个输出token完全一致；关闭缓存后在第3个token的缩进处分歧，
该位置缓存路径的首选候选分数相同，不能仅据此判定缓存错误。无缓存运行约93秒仅生成26个token后触发时间限制，
因此没有完成无缓存任务语义对照。原始诊断为 `outputs/toy_vlm_cache_diagnostic_20261115.json`，
不能把这次检查说成已证明两种推理方式完全等价。汇总状态在 `outputs/toy_vlm_trial_20261115/status.json`。

## 现在可运行的可视化采集

在仓库根目录运行；不需要启动 VLM 服务，当前使用规则教师生成采集标签。

```bash
./experiments/microduck_tasks/toy.sh \
  --command '先点头，再坐下，再站起来' \
  --command '先踢蓝球，再踢红球，再原地转一圈' \
  --command '你现在能看到什么'
```

窗口显示外部视角、前方/近处相机、回复、当前目标与剩余步数。每个目标验收后再进入下一个目标，
期间可以在窗口或终端输入“你现在能看到什么”“停下”等。人工输入会接管后续预设命令；
普通聊天保留当前任务队列，“停下”取消当前任务及剩余目标。关闭窗口会停止并保存最终记录。
窗口保持开启时物理轨迹仍会增长，检查完成后关闭即可。

自由交互：`./experiments/microduck_tasks/toy.sh --interactive`。
随机位置：加 `--layout random --seed 203`。无窗口采集加 `--no-viewer`；该演示模式把持续行走限制为约一秒，
然后记录自动发出的“停下”，避免脚本无限等待。正式持续任务应由真实用户或采样脚本明确结束。
默认输出到 `outputs/toy_demo_<时间>_<随机后缀>/`，包含双相机 PNG、事件、轨迹、来源和验收结果。

本次最终小样本在 `outputs/toy_pilot_verified_20261115/`：11 个片段、84 条对话，
34 个目标通过验收、3 次正常暂停/取消，另有 1 次特意设置的目标找不到：搜索达到上限后失败并清空后续任务。
全部 13 个自身表演动作均执行过；最终 `dataset_final/` 含训练集 79 条、验证集 5 条。
连续任务包括蓝球→红球→整圈、黄球→蓝球→反向整圈、走到黄球旁→踢蓝球→整圈、点头→坐下→站起。
前一轮 `toy_pilot_20261115` 暴露了常见动作别名未覆盖的问题，仅保留作诊断，最终导出不包含它。
最终数据、图片和物理轨迹合计约 65 MiB，其中导出训练数据约 4.1 MiB。
详细结果见该目录 `report_with_failure.json`；此前 `report.json` 和 `dataset/` 保留原 81 条版本供追溯。

全部 84 条通过真实 Qwen3.5 processor 检查，输入不参与 loss、完整助手 JSON 参与监督，无截断。
另从训练集取两条三目标样本，冻结 Qwen3.5-2B 和原始词表输出层，仅训练 rank-4 输出残差三步：
完整 JSON loss 从 0.85464 降到 0.79607，约 100 万可训练参数，显存分配峰值约 1997 MiB。

训练标签只表达接受时的将来意图，未把执行结果改写为成功。
这证明数据和反向训练链路可用，不是训练质量或泛化成绩，
该适配器未接入执行器，也没有替换已有技能头。

## 首版冻结 VLM 的技能选择器

本轮使用 `toy_diverse_20261115_2020/dataset` 的全部 2,562 条样本，保持既定 train/val/test 分组。
冻结本地 Qwen3.5-2B，以双相机、用户文本、公开历史和状态的最后一个有效输入 token 向量为特征；
标签和助手目标回复不进入特征提取。相同提示词、图像预处理和特征配置同时用于训练与在线推理。
主干采用 NF4 量化；缓存特征为 2,048 维。候选小头为 64/128 隐层的共享 GRU 解码器，
分别约 17 万/39 万参数，只用验证集选择，选择结束后评估测试集一次。

小头学习八种 decision 与最多六个按顺序排列的语义目标，以及各目标适用的颜色、次数、角度等字段。
不同位置共享解码器，没有把完整六步组合当成一个分类标签；是否能泛化到新组合仍由独立评估决定。
数值目前仅支持语料出现过的值：移动 0.6/8 秒，转向 30/90/180/360 度，重复 1–3 次；
目标限红/黄/蓝球，接近距离固定 0.25 米。这不是任意数值、任意物体或底层运动控制模型。
回复仍使用明确模板，完成/失败反馈取自执行器；停止与暂停保留本地处理。
选择器输出错误时保留原始预测，合同校验可拒绝执行，不用规则教师改成正确动作。

2026-11-15 首批基准约 3.2 秒/条，完整提取实测平均 3.58 秒/条，共 9,176 秒，约 2 小时 33 分钟；
batch=2/4 反而更慢，故训练缓存和在线推理均使用 batch=1。两候选小头 CPU 训练与离线报告实测共 18.23 秒。
特征逐条原子保存，可用原命令加 `--resume` 继续；已缓存特征之后重训无需再次运行 Qwen。
完整批量基准为 `outputs/toy_selector_feature_benchmark_20261115.json`。
`outputs/toy_selector_random_feature_diagnostic_20261115` 只用于验证训练程序，随机特征成绩不是模型效果。

## 用户说什么，应答复什么

名字暂用可配置身份字段 `identity.name=小鸭`；不把名字烙进动作标签。
不要求每个控制 tick 都讲话；每个用户回合必须有答复，重要完成/失败事件再追加简短反馈。

| 用户示例 | 期望回复 | 任务含义 |
|---|---|---|
| 你好，你叫什么 | 你好，我叫小鸭！ | 纯聊天，不更改现有任务 |
| 你都会做什么 | 按当前能力列举，说明动作空间要求 | 能力问答，不逐个演示 |
| 你会前滚翻吗 | 我有这个动作，要宽敞空间 | 问能力；不自动翻 |
| 能不能给我做个前滚翻 | 好，我做一次前滚翻，再站稳 | 礼貌请求，可执行一次 |
| 做一下前滚翻 | 同上 | `perform(roll, repeat=1)` |
| 走到黄球旁边，别踢 | 我靠近后停下，不踢 | `navigate`，不是 `kick` |
| 一直往前走不要停 | 持续前进，收到停止或本地保护事件就停 | `move(until_cancelled)`，不是一次短走 |
| 停下 | 收到，正在停下 | 先撤销运动授权和任务队列；确认后才说“停好了” |
| 坐下，先别起来 | 坐下后保持坐姿 | `posture(sitting)`，不能替换成坐站循环 |
| 先踢蓝球，再踢红球，再原地转一圈 | 复述顺序，逐项确认完成再继续 | 三个语义目标，各有独立目标和完成条件 |
| 别踢蓝球，改踢红球 | 取消蓝球任务，改踢红球 | 原子替换剩余任务 |
| 踢完再点头 | 完成当前踢球后点头 | 追加任务，不重新踢一遍 |
| 暂停，等我说继续 | 请求暂停，保留未完成任务 | 暂停与取消分开；“停下”默认取消 |
| 继续 | 有暂停任务则恢复；已取消或无任务则澄清 | 重新观察后恢复语义目标，不重放旧速度队列 |
| 把球叼起来 | 当前玩具模式不执行叼取 | 拒绝，不自行改成踢球 |
| 先踢红球再叼回来 | 说明含不支持能力，整组先不启动 | 禁止悄悄执行前半段 |
| 你看到了几个球 | 只根据当时可用观察回答 | 遮挡/视野外的球不能靠场景真值计数 |
| 刚才踢到了吗 | 根据接触和位移反馈回答 | 执行完一段踢腿不等于踢球成功 |

上表是目标语义，不能据此推断所有措辞均被当前规则解析器覆盖。
坐姿保持、独立停靠、累计角度转向、持续运动和组合队列已接入并实测；
停止后再回答画面的复合请求等仍需扩展，当前会说明需重新观察，不拿停止前图片冒充停止后图片。

## 视觉对话与下一步实施顺序

“你现在在能看到什么”“描述一下眼前的画面”“红球在哪边”都属于对话，具体是依赖视觉证据的对话。
纯文字聊天主要依赖公开历史与身份；视觉对话必须读取当时相机画面。两者都可输出 respond 和空 goals，
不会清空正在执行的任务。数据统计单独区分 text_chat、visual_dialogue 和 action_request，
这些是采样/评估标签，不额外塞进技能分类器，也不必增加模型输出字段。

视觉描述应覆盖物体类别、颜色、数量、相对方位、空间关系、局部遮挡和不确定性，不局限于球。
本轮增加了紫色方块的设计病例，它属于未来视觉理解示例，不表示现有三色球检测器已经能识别方块。
描述能力可以扩展到其他物体，而物体交互候选仍仅限踢球。

实际接入时必须区分“拿到图像但没检测到球”“没有收到图像”“图像已过期”。空 entities 不能代替相机状态，
所以接入多模态消息时还要明确每路图像的可用性、采集时间及新鲜度。front/near 可能看见同一颗球，
没有可靠的跨相机关联时分别描述，不直接相加计数。左右采用机器人自己的朝向；只根据当前可见证据回答，
不能读取隐藏世界的完整物体列表，也不能把“没看见红球”写成“场景没有红球”。

“能看到红球吗”本身不授权转向搜索；“向右转，看看有什么”包含动作和后续视觉答复。
“先停下，再告诉我你看到了什么”应立即处理停止，保留待回答的问题，停稳后读取新图像再回答。
这类执行后答复需要执行桥记录未完成的对话请求，不能用执行前图像冒充动作后的观察。

原定实施顺序如下。第 1–3 步已完成规则教师、小样本验证和首批多样化采集；
首版技能头训练已经完成但泛化不达标；基础 VLM 的自由对话/视觉质量评测和更广泛语料扩展尚未完成：

1. 先接最小在线对话链：实际相机消息、公开历史、回复输出及任务状态，完成纯聊天和视觉问答，
   验证每轮有答复、描述有依据、聊天不改变任务。先使用基础 VLM 评测，不急于微调。
2. 接入新版任务管理：单动作、停止/替换、暂停/恢复、组合队列；补齐坐姿保持、独立停靠、累计角度转向和持续运动。
   所有能力只在真实验收通过后加入在线能力快照。
3. 用相同在线输入/输出接口试采少量完整多轮对话，保存真实图片与可信结果，人工抽查和输入回放通过后再扩充。
   视觉回复采用基于画面的审核标注；不能让未经核实的模型回答直接成为正确答案。
4. 再分组导出对话 SFT 和技能选择样本，训练冻结主干的小技能头；只有基础 VLM 的对话规划确有不足时，
   才针对对应问题做生成式微调，分别报告视觉事实、任务完成和中断表现。

## 新输入与输出

输入由宿主组装：身份、当前事件、最近公开对话、当前可观察实体/姿态/新鲜度、本地运动许可、
当前任务及待执行队列、最近可信结果、真实能力目录。用户文本只是 `event.text`，不能覆盖状态或能力。
目标使用 `category + attributes + entity_id`，颜色只是 attributes 中的一项，不设置顶层 ball_color。
当前搜索能力仍只有红/黄/蓝球；可扩展结构不意味着已经具备其他感知或物体交互能力。

输入严格校验见 `toy_inputs.py`；输出严格校验见 `toy_protocol.py`；生成式解码的 JSON Schema 见 `toy_schema.py`。
结构校验不能证明语言理解正确：是否读懂否定、有没有虚假承诺，仍需审核和模型评测。

```json
{
  "schema_version": "microduck-dialogue-3-pilot1",
  "reply": "好，我先踢蓝球，再踢红球，最后向左转一圈。",
  "decision": "replace",
  "goals": [
    {"type":"kick","target":{"category":"ball","attributes":[{"name":"color","value":"blue"}],"entity_id":null}},
    {"type":"kick","target":{"category":"ball","attributes":[{"name":"color","value":"red"}],"entity_id":null}},
    {"type":"turn","direction":"left","angle_deg":360}
  ]
}
```

`decision` 只有八种：respond、clarify、decline、replace、append、cancel、pause、resume。
前三种保持现有任务；replace/append 必须给出至少一个目标，其余必须为空 goals。整组先校验再提交。
能力快照另有 max_goals 和 queue_control；按最新需求，当前在线执行器使用 `max_goals: 15`。单次计划最多15项目标，追加后的 `active + pending + 新增` 总数也最多15；16项或累计超限整组拒绝，不截断。旧显式 `max_goals: null` 仅保留为历史接口兼容；旧正整数快照仍按其明确容量校验，用户文字不能改写当前上限。
历史设计病例里的 current/planned 是能力约束测试配置，不代表当前在线执行器仍只支持单目标。
旧 H0 六步小头、Q0/Q1 冻结数据与成绩仍保留旧语义；Q1 权重未为15项容量和安全暂停重新训练。当前协议接受7至15项不能视为旧模型已经学会长计划；新训练和新评测须单独版本化。模型上下文、输出 token 预算和执行等待超时仍需分别处理，不能静默删掉超出预算的目标。
`reply` 去空白后不能为空；所有对象拒绝未知字段，数字拒绝 NaN/Inf/布尔伪装。
这里描述的是在线完整对话协议。已完成的 Q0/Q1 P6 实验只监督和生成 `decision + goals`，并不生成此处的 `reply`。Q1 checkpoint100 在开发集 20 条应当 `respond` 的样本上为 20/20；报告明确 `reply_quality_scored=false`，不能把这个比例当作聊天质量。评测包装器补入的“离线规划评估，尚未提交执行。”也不是模型回答。
同色多球需澄清或绑定唯一观测 ID；ID 与属性冲突拒绝；不可见目标必须有对应搜索能力。
所有已绑定目标在真正执行前还要重观测；计划接受时的对象位置不能沿用到后续数十秒。

| 目标 | 参数 | 必须由执行器验收的含义 |
|---|---|---|
| perform | action、repeat=1..3 | 完整动作周期和恢复；repeat 是完整表演次数，不是关节震荡峰值数 |
| kick | 独立 target | 搜索→接近→选脚→踢→恢复；确认目标接触与位移；失败不能推进下一目标 |
| navigate | target、standoff_m | 平面身体坐标距离进入指定停靠带并站稳；不得踢球/推球；默认 0.25 m |
| move | direction、duration 或 until_cancelled | 有限移动结束后停；持续任务直到取消/保护触发；后面不能排永远轮不到的目标 |
| turn | direction、angle_deg | 累计实测转角，360°不是最终朝向相同；同时检查位移漂移 |
| posture | standing 或 sitting | 完成姿态转换后持续维持；聊天和队列清空不自动站起 |

`angle_deg` 只用于语言层；执行桥按库的单位规范转换为弧度。
导航停靠容差、持续停稳时间、完整转圈的角度/位移容差、动作实际空间范围必须先测量定标再冻结版本，
不能凭一个理论阈值把真实轨迹自动判成功。已有踢球保留原独立接触和位移验收。

## 队列、连续性与中断

高层 goals 是用户任务；执行 chunk 是控制器内部的短动作。一次 kick 可以包含许多搜索和接近 chunk，
不能把三秒的 chunk 预算当成三秒必须完成所有任务。完整滚翻等也不能任意切换成站立造成失稳。

安全暂停不会取消推理或丢弃剩余计划。有限目标完成整个动作及稳定恢复后，已完成目标移出队列，只挂起尚未执行的目标；持续行走在短段边界收稳后，保留同一持续目标。恢复从保留的 `active` 继续，不重演已完成动作；若最后一项已经完成则回到空闲，没有旧动作可恢复。推理期间的暂停由宿主锁存，新计划生成后完整保留为 `paused`，不先开始第一项。`pause` 和 `resume` 的 `goals` 均为空。

执行桥使用宿主生成的任务 ID/步骤 ID/代次。停止输入先增加取消代次并锁存停止信号，不等待正在进行的模型推理、
普通输入队列或状态/世界锁。停止前排队的指令、迟到的动作计划和对应回复不再提交；原始模型结果保留为审计记录。
执行器按任务修订号和取消代次核对结果，避免旧成功事件推进新任务；启动新任务前再核对取消代次。
执行锁内提交队列，模型只建议目标，不写电机或修改控制状态。

当前明确“停/停下/停一下/别动/不用做了”等走本地停止路径，否定“不要停”和引用“读出‘停下’”不误判；
停止取消当前任务并清空余下目标，已取消任务不能用“继续”恢复，停止后新的明确任务仍可执行。
嵌套踢球控制器保留父任务的停止标记；入口和会话均已覆盖阻塞推理、旧输入、迟到结果、长队列取消的并发回归。
这验证了文本输入后的取消处理，不代表已测量语音识别耗时或真实机器人的停稳时延；当前模型后端仍采用锁步仿真。
有歧义的语音可先安全暂停并澄清。普通聊天不取消运动，接受追加也不重启正在执行的动作。
紧急停止不得等待 HTTP；滚翻等不可任意中断阶段还需本地、限时的安全收尾策略和实测停止延迟。

当前持续行为以 0.2 秒短段执行，每段重新观察；桌面产品还需独立控制进程租约和看门狗，
保证丢失控制进程/新鲜观察/本地许可就停止。规划可以与当前合法动作并行，
但新结果必须通过代次和新鲜度检查，不能无条件播放缓存的多步动作。
桌面产品还需要实际的桌边/障碍检测；本机地面仿真没有这个能力。设计病例中的 desktop 未接保护时拒绝移动、滚翻等动作，
不把一句“持续往前走”解释成可无限越过桌边的命令。

## 如何形成正确的微调数据

先固定任务语义和可执行器，再采集。加入视觉对话后共有 209 个设计病例、97 个语义家庭用于评审和合同回归，
没有 train/val/test 分割；不能拿这组人工已知答案算模型成绩。生成命令：

```bash
/home/luckysir/microduck/microduck_rl/.venv/bin/python \
  -m experiments.microduck_tasks.build_toy_casebook \
  --output experiments/microduck_tasks/outputs/toy_dialogue_review_new
```

产物为完整 `design_cases.jsonl`、便于查看的 `review.tsv`、能力清单、输出 Schema、提示词和源码哈希。
命令拒绝覆盖旧目录；导出检查强制拒绝把设计病例改成 training_ready。当前在线输入序列化复用
`model_payload`，把相机图像另作为多模态消息传入；病例当前 media=[]，不能伪装成视觉 SFT。

真实采集按以下顺序进行：

1. 补齐本轮明确缺失的执行语义，先在相同接口跑规则/模板教师，记录完整多轮任务；
   对回复、停止、目标顺序、姿态保持、导航不误踢分别做验收。先完成小规模试采和回放，再扩大数量。
2. 为每个场景制定语义脚本，再生成口语改写：直接/礼貌请求、能力问句、否定、纠正、省略、次数、顺序、聊天插入。
   改写后重新做语义审核，不因文字相似就复制标签。未支持动作也要有足够拒绝示例，不能只收成功踢球。
3. 每个决策时刻保存当时真实图像、公开历史、可观察状态、当前目标和已有反馈，以及教师输出。
   相机时间不得晚于决策；未来结果只能进后续反馈样本。训练输入不能含最终成功标签、隐藏球坐标、脚选择答案。
4. 记录口头接受、动作开始、成功/失败/取消分开的事件。轨迹失败保留用于分析；正确恢复、澄清、拒绝、正常用户取消
   都可成为相应任务的正例，不能把“取消”伪造成完成，也不能把失败动作当作该动作的正确示范。
5. 随机场景位置、颜色与位置对应、朝向、遮挡、双同色球、相机噪声、开始姿态和前序动作；
   加入相同指令不同状态、相同图像不同指令的配对。颜色不能和左/右脚形成固定对应。
6. 先按完整对话/轨迹、场景种子族和语义改写来源分组，再划分数据；相邻帧、同轨迹所有改写和图像增强一起归组。
   额外保留未见表达、未见场景、未见组合顺序、执行中停止/改目标四类测试。不要逐帧随机拆分。
7. 输出语法、能力、目标绑定、时序、来源、成功证据和输入回放一致性全部检查；同一输入交给教师和学生执行器
   应使用同一合同。记录 schema、目录、执行器、感知和模型版本哈希；任何实质语义变动都重新导出/提特征。

试采配比可先用聊天/能力/视觉问答约 25%，单动作约 25%，组合任务约 20%，多轮指代/暂停/取消约 20%，
歧义/能力拒绝/失败反馈约 10%，再按实际失败和覆盖调整。这是采样起点，不是论文证明的最优比例。
除了条数，还应统计每项动作的进入状态、目标位置、顺序组合、每种拒绝原因和中断阶段是否有覆盖。
为了省空间，优先存决策边界图像和必要的故障片段，不把所有 50 Hz 相邻图像都当成独立 SFT 样本；
物理轨迹可保留紧凑状态记录，人工评审视频按需渲染。

## 与冻结 VLM 技能头的关系

最终分三层：对话规划（回复和 goals）→ 任务队列/本地闭环 → 当前任务下的技能选择与已训练运动策略。
聊天不向底层输出一个假 stand；它只是保持任务状态。成功反馈由事实驱动，不能依赖模型自称 finish。

已有“冻结 Qwen3.5 特征 + 小分类头”仍适合快速验证最底下的技能选择，但 11 个分类标签不可能同时表达
任意句子、多个目标、参数和队列操作。增加一个 answer 类也不能让分类头生成自由聊天。
因此保留两种明确的数据视图：对话 SFT 学 `reply + decision + goals`，技能头样本学当前活动目标下的下一技能。
二者共享真实观察和已发生反馈，但目标标签、时序频率、评估指标不同，不能强行并成一个颜色任务分类器。

先用规则/模板基线落实完整对话执行链，技能头继续保持冻结主干的小模型训练方案；
之后若基础 VLM 不能稳定生成上述结构，再单独评估对话规划层的生成式 SFT/LoRA。
本轮仅运行了上文的三步生成式训练探针，未完成正式训练或模型闭环评估。

评估分别报告：每回合应答率、聊天事实正确性、计划与目标顺序、澄清/拒绝、真实任务成功率、
停止延迟与旧计划复活次数、失败后恢复、虚假完成率。当前合同测试只证明代码拒绝了相应非法数据，
不证明模型理解正确。组合任务的执行证据来自独立 MuJoCo 小样本，不等于模型自主规划成功。
