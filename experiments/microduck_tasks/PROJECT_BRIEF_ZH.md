## 产品目标与当前范围

### 必须具备的交互

每一句用户输入都应得到合适的答复。纯聊天可以不执行动作；动作请求应给出计划并执行；不支持或有歧义的请求应如实解释或澄清。接受任务、开始动作、执行完成和失败必须区分。

| 类别 | 用户表达示例 | 期望行为 |
|---|---|---|
| 问候与身份 | 你好、hello、你叫什么 | 自然回复，身份由宿主设定为“小鸭” |
| 能力问答 | 你都会做什么、你会前滚翻吗 | 介绍当前真实能力，问能力本身不自动触发动作 |
| 视觉对话 | 你现在能看到什么、蓝球在哪边 | 根据当前画面和可靠感知回答，不臆造物体或方位 |
| 单动作 | 点点头、做一下前滚翻 | 调用对应技能并报告真实结果 |
| 姿态保持 | 坐下、站起来 | 坐下后保持，不把“坐下”解释成坐下再自动站起 |
| 到达目标 | 走到黄球旁边 | 搜索、接近并停靠，不自动踢球 |
| 物体交互 | 踢蓝球 | 找到目标、接近、站稳、踢球、恢复并验收 |
| 持续任务 | 一直往前走不要停 | 持续执行，直到明确取消或本地保护触发 |
| 中断控制 | 停下、暂停、继续 | 区分取消与暂停，正确保留或清空队列 |
| 组合任务 | 先点头，再坐下，再站起来 | 保留顺序，逐项完成并验收 |
| 多物体组合 | 先踢蓝球，再踢红球，再原地转一圈 | 每步独立绑定目标，完成前一步后重新观察 |
| 执行中聊天 | 走路时问“你叫什么” | 回答问题，保持原任务语义 |
| 修改任务 | 再加一次点头、改成踢红球 | 明确追加或替换，旧任务结果不能推进新任务 |
| 不支持与歧义 | 后空翻、叼起物体、两个同色球未指明哪个 | 拒绝或澄清，不偷偷替换成前滚翻或俯身 |

上述表格是产品期望。当前规则教师只理解有限的已定义表达；基础 VLM 和已训练小头也都没有达到全部要求。

### 已确定的范围取舍

- 优先在本台电脑把流程和模型效果跑通，再考虑 Radxa 等边缘部署。
- 正式任务保留仿真中已初测的自身动作；涉及物体操作的任务仅保留踢球。可以走到球旁，但不采集叼取、搬运、投掷、推方块作为当前玩具能力。
- 先学习任务与技能层，复用已有低层运动权重。目标是技能级分层 VLA，而非直接由语言模型输出所有电机目标。
- 当前交互默认使用 MuJoCo 原生窗口与右侧灰色中文聊天框；终端和旧 Web 入口保留用于调试。连续语音识别、语音合成、唤醒和完整语音产品链尚未接入本轮流程。
- 当前世界是地面仿真。真实桌边检测、真实桌面移动和滚翻安全性不在已验证能力之内。

### 仿真与实机输入的差距

旧视觉执行路径使用 `front`、`near` 两路 320×240 RGB-D，相机固定在躯干。旧 VLM 接收两张 RGB 图，结构化实体位置则依赖深度投影。
实机脸部有 RGB 和激光测距，尚没有证明能原样提供仿真的双路画面和稠密深度派生实体。激光实测距离属于可用传感器观测，
不属于仿真隐藏真值；但需确认返回距离属于目标球，而不是同一测区中的地面、背景或其他物体。

2026-11-16 新增独立的 [RGB＋8×8 测距仿真支路](RGB_TOF_SIM_ZH.md)：相机与测距随头运动，
以关节正运动学更新标定，按距离动态投影测区，融合 RGB 球轮廓与粗测区表面距离；
身体姿态和停稳来自模拟 IMU/编码器估计。控制器不读取球世界坐标、理想基座姿态或线速度。
静态 14–60 cm 八例均识别；接近红球基线 4/4、5 mm 噪声＋10% 丢测 4/4 通过独立验收。
完整踢球已有成功轨迹，但侧向布局尚不稳定，全部成功/失败见独立报告和各批 summary。
出脚前恢复头姿，使用不超过 1.4 s 的 ToF 位置记忆和新 RGB 轮廓复核，不宣称全程都有新 ToF 回波。
该支路使用暂定安装尺寸与测距模型，未替换旧训练数据，也尚未完成实体联调。

### 机器人本体与低层策略

机器人基础项目为 [Pollen Robotics Microduck](https://github.com/pollen-robotics/microduck)。本机另有 HD1910 适配后的 MuJoCo 几何、BAM 电机模型和训练权重。当前行走权重为本地 `hd1910_walk_1849.onnx`，坐站、俯身、前滚翻复用已有 HD1910 权重。

左右踢球来自 [pollen-robotics/microduck-policies](https://huggingface.co/pollen-robotics/microduck-policies)，本地固定 revision 为 `236d1835b03ac7b45d962efbf2fe3a6940206112`。另外下载了社区动作权重；23 份公开 ONNX 合计约 19.07 MiB，详细 URL、revision、SHA256 和许可记录在 [action_weights.json](action_weights.json)。

普通低层策略主要是 `61 维本体状态及命令 → 14 维关节动作`，控制频率 50 Hz，仿真物理频率 200 Hz，HD1910 BAM 延迟配置为 20 ms。踢球网络本身不接收“蓝球”等颜色词、自然语言或图像；找哪个球、何时踢、选哪只脚由上层完成。部分特殊动作还带循环状态或打包时间线。

部分社区权重未声明许可证，包括当前使用的若干舞步、滑步。公开可下载不等于已经取得商业玩具再分发许可，产品化时需要逐项处理。

## 现在的系统架构

```text
用户文本 + front/near 图像 + 公开对话历史
             + 感知状态 + 当前任务队列 + 已发生的执行结果
                              │
             ┌────────────────┼─────────────────┐
             │                │                 │
         规则教师        冻结 Qwen + 小头      原始 Qwen 生成 JSON
             │                │                 │
             └────────────────┼─────────────────┘
                              ↓
                 reply + decision + goals
                              ↓
             协议校验、能力检查、目标绑定、任务队列
                              ↓
             本地导航 / 姿态 / 转向 / 踢球执行控制器
                              ↓
                 现有 ONNX 策略 → 关节目标
                              ↓
              MuJoCo 物理执行 → 结果验收 → 新观察
```

以下后端共用执行层，但结果来源不同：

| 后端 | 理解与规划来源 | 回复来源 | 用途 |
|---|---|---|---|
| `teacher`，旧采集入口默认 | 手写语义规则与模板、闭环教师 | 模板及感知事实 | 采集有监督数据、验证执行器；新桌面入口仅显式调试 |
| `selector` | 冻结 VLM 特征加已训练小头 | 模板 | 验证小头能否泛化 |
| `vlm` | 基础 VLM 直接生成结构化内容 | VLM 生成 | 无本任务正式微调的对照 |
| `q1r`，原生桌面默认 | Q1R PyTorch LoRA `checkpoint_000513` 生成 `decision + goals + reply` | 模型生成 | 当前中文对话与任务规划入口 |
| `q1`，历史对照 | Q1 LoRA checkpoint100 生成 `decision + goals` | 宿主模板 | 旧规划模型；未为15项目标重训 |

Q1/Q1R 使用文本与结构化状态输入，不把原始 RGB 图片传给模型。桌面入口默认仍调用旧 RGB-D 执行桥；
新增 RGB＋ToF 支路尚未接入这个默认入口。

旧规则演示“知道自己叫小鸭”，来自身份配置和规则回复，不证明基础模型拥有关于这台机器的长期记忆。模型模式中的身份也由输入提供。

### Strands Robots 在其中的作用

项目位于 Strands Robots 仓库，但当前实验只直接复用 `Policy`、`Observation`、`JointState`、`Pose`、GL 渲染线程以及投影重力工具等基础接口。

当前 MuJoCo 主循环、模型加载、相机感知、任务队列、停止逻辑、录制和验收主要由 `experiments/microduck_tasks` 自建。没有用 Strands Agent 自动规划，也没有通过库的 `Robot`、`Simulation`、Dashboard、Mesh 或实体 Microduck 驱动运行本轮任务。库的真实机器人安全链也没有自动包住这套自建仿真执行器。

## 标准化输入与输出

### 输入

当前协议版本为 `microduck-dialogue-3-pilot1`。输入由宿主构造，用户的话只进入 `event.text`，不能覆盖真实能力和身体状态。两张图像作为独立多模态内容传入，不把像素写在 JSON 里。

| 字段 | 内容 |
|---|---|
| `schema_version` | 当前协议版本 |
| `identity` | 机器人名字，目前是“小鸭” |
| `event` | `user` 或可信执行器 `feedback`，及当前文本 |
| `history` | 最近最多 12 条公开用户与助手消息 |
| `observation` | 观察年龄、实体、姿态、是否静止、环境与运动许可 |
| `execution` | 执行状态、当前目标、后续队列、上次真实执行结果 |
| `capabilities` | 本轮可用目标类型、自身动作、搜索目标、队列容量与控制能力 |

宿主内部有队列代次 `execution.revision`，但 `model_payload()` 在送入模型前将其删除。训练输入不包含当前回合的正确答案或尚未发生的成功结果；已经发生的历史结果可以作为反馈进入后续输入。

实体使用 `id + category + attributes + position_body_m + confidence`。颜色是属性，例如 `attributes:[{"name":"color","value":"blue"}]`，不再设置顶层 `ball_color`。

目前实体检测仍只可靠覆盖红、黄、蓝球：RGB 颜色阈值、区域提取、深度投影和已知球半径拟合，并非通用目标检测器。每种颜色合并为一个实体的实现尚不支持真正的同色多球跟踪。结构更通用不代表感知能力已经通用。

### 输出与真实例子

下面是用户曾运行的规则教师演示中的真实输出，不是训练后模型的成功预测：

用户：“先踢蓝球，再踢红球，再原地转一圈”。

```json
{
  "schema_version": "microduck-dialogue-3-pilot1",
  "reply": "好的，我会依次执行：踢蓝球，然后踢红球，然后向左转360度。",
  "decision": "replace",
  "goals": [
    {
      "type": "kick",
      "target": {
        "category": "ball",
        "attributes": [{"name": "color", "value": "blue"}],
        "entity_id": null
      }
    },
    {
      "type": "kick",
      "target": {
        "category": "ball",
        "attributes": [{"name": "color", "value": "red"}],
        "entity_id": null
      }
    },
    {"type": "turn", "direction": "left", "angle_deg": 360}
  ]
}
```

八种 `decision` 分别是回复 `respond`、澄清 `clarify`、拒绝 `decline`、替换任务 `replace`、追加 `append`、取消 `cancel`、暂停 `pause`、恢复 `resume`。当前默认只有 replace/append 带 1 至 15 个目标，追加后的 `active + pending + 新增` 总数也不得超过15；其他决策的 goals 必须为空。reply 必须非空。

| 目标类型 | 主要参数 | 语义 |
|---|---|---|
| `perform` | action、repeat | 完整自身动作，可重复 1 至 3 次 |
| `kick` | target | 搜索、接近、踢球并恢复 |
| `navigate` | target、standoff_m | 到球旁停靠，不踢球 |
| `move` | direction、limit | 有限时长或直到取消的移动 |
| `turn` | direction、angle_deg | 按累计实际转角执行，包括完整一圈 |
| `posture` | pose | 坐下保持或站起 |

协议允许移动 0.12 至 10 秒、转角 15 至 360 度、停靠距离 0.15 至 0.5 米；但当前学习小头的输出词表更窄，见下节。所有对象拒绝未知字段，非法数值和不满足状态条件的计划也会拒绝。

JSON 可解析、协议合法、动作语义正确是三件不同的事。模型生成合法的“前滚翻”结构，也可能错误地回答了“后空翻”的请求。

## 冻结 VLM 技能选择器怎样训练

当前正式训练方案是：冻结 Qwen3.5-2B，先离线提取输入特征，再用标签训练小网络。

```text
双 RGB + 指令 + 历史 + 状态
           ↓
冻结 Qwen3.5 多模态主干
           ↓
最后一层、最后一个有效输入 token 的 2048 维隐藏状态 h
           ↓
按训练集统计量标准化
           ↓
Linear 2048→128 + GELU，训练时 Dropout 0.15
           ↓
128 维上下文 z
           ├── Linear → 8 类 decision
           └── GRU → 有序目标类别及参数 → EOS
```

这个向量是模型内部的上下文状态，不是生成回复后的文字向量，不是词表概率，也不是仅来自视觉编码器的图像特征。取最后有效位置是当前设计选择，不保证它是对全部图像和任务信息的最优压缩。

投影层将全部 2048 个数进行可学习的加权组合，得到 128 个数；不是挑选原向量中的 128 个位置。GRU 每一步结合固定上下文、上一个目标及参数和内部状态，预测下一个目标，最多六步后结束。它没有把每种完整组合当成单独类别。

训练时用正确的前一步目标作为条件；推理时依赖自身上一预测，因此前一步错误可能影响后续步骤。损失包括决策、目标类型和适用参数的分类误差。Qwen 权重不更新；所有特征缓存完成后，重复训练小头很快，但新指令在线仍要经过 Qwen。

当前选中模型有 388,728 个可训练参数。输出能力有硬限制：目标仅三色球、`entity_id=null`，停靠距离固定 0.25 米；移动时长仅 0.6 或 8 秒；转角仅 30、90、180、360 度；重复次数 1 至 3。它不能表达任意数值或任意物体。

**这次小头没有训练自由语言回复，也没有训练新的电机控制策略。** 小头学 decision 和 goals，程序生成回复模板并调用已有技能。若要完整学习自然对话和视觉描述，需要另外的生成式路线。

### 可训练性检查与已经完成的训练

所有 2562 条正式样本通过真实 Qwen processor 检查：图片可读、输入不计入生成式 loss、完整助手 JSON 可被监督、没有静默截断，最长完整输入输出约 1525 tokens。

此前还用两条三目标样本做过三步生成式反向传播探针：冻结基座和词表输出层，只训练 rank-4 输出残差，loss 从 0.85464 降到 0.79607。这只证明链路能反向训练；该适配器没有成为可用对话模型。

随后已经正式完成当前 388,728 参数的技能小头训练。尚未完成当前 toy 协议下、覆盖全部对话和视觉描述的正式生成式 SFT/LoRA。早期 v1 的 QLoRA 是另一轮任务与协议。

### 已确认的采样偏差

当前数据里，空历史直接下达的动作全部是移动。自身表演、踢球、导航、转向、姿态和组合任务都出现在两条公开历史之后，多数前面是固定问候。验证和测试也沿用了这种结构。

因此，模型可能把“前面有没有问好”与“现在是否应该执行动作”错误关联。四个事后诊断案例固定图像、指令和身体状态，只加入采集时的问候历史，动作决策从 0/4 正确变为 4/4，但完整计划仅 2/4 正确；剩余错误包括选错颜色和多加一步动作。

这是偏差影响这些案例的证据，不是靠前置问候修好了模型。除了总量，还必须解决有效动作监督少、长组合覆盖少、任务与对话位置混杂的问题。

| 验证集完整动作计划正确 | 9/42，21.4% |
| 测试集完整动作计划正确 | 12/54，22.2% |
| 测试未见计划正确 | 6/42，14.3% |
| 测试单目标、双目标、六目标 | 8/42、4/6、0/6 |
| 测试三至五目标 | 没有样本，不能给出结论 |

decision 只是“是否启动、回复、取消”等大类。97.1% 不代表已经选对技能、颜色、顺序和参数。训练与留出集合的计划准确率差距明显，当前版本不具备部署质量。

### 独立仿真与原始 VLM 对照

同一开发评估组有 14 个场景、19 条用户消息，其中 17 次模型调用，另两次停止或暂停由宿主处理。

| 路线 | 原始模型决策及全部目标严格匹配 | 完整有限任务正确且执行通过 | 平均模型响应 |
|---|---:|---:|---:|
| 冻结 VLM 加训练小头 | 8/17 | 0/9 | 3.33 秒 |
| 原始 VLM 加 full 提示 | 6/17 | 1/9 | 8.97 秒 |
| 原始 VLM 加 compact 提示 | 6/17 | 2/9 | 8.02 秒 |
| 相同场景规则教师 | 教师诊断 19/19 回合正确 | 9/9 | 不与模型推理延迟混算 |

小头的九个有限任务中，原始输出是八次 decline、一次 clarify，因此任务没有启动；不是低层策略尝试九次后摔倒或踢空。

两种原始 VLM 提示各有 17/17 条能解析成 JSON，但仅 10/17 条通过完整协议和当前状态检查。已经成功执行某个目标，也不代表执行了用户真正要求的目标。

compact 提示包含四个上下文示例，且依据初版错误调整过，因此应称“无本任务微调的提示方案”，不能把这组回归结果当成严格零样本、完全未见的最终测试。它仍保留完整任务上下文，系统提示约 2400 tokens。

直接生成目前有以下真实错误：漏掉三步任务中的点头；把一圈写成 30 度；口头承诺动作却输出空 goals；把后空翻映射为前滚翻；臆测球颜色或方位；把不同相机看到的内容混淆。

另有 20 条语言与状态诊断，14 条协议合法、7 条计划严格匹配；允许等价实体绑定后，8 条模型计划合法且语义正确。该诊断不执行物理动作，部分状态是明确构造的反事实，不能当作机器人实测成功率。聊天自然度和视觉事实可靠性仍只有小规模人工检查。

### 训练与推理成本

- 全量 2562 条冻结特征提取共约 9176 秒，即 2 小时 33 分钟，平均每条 3.58 秒。
- 两候选小头 CPU 训练加离线报告共 18.23 秒。所谓“方案一训练快”，主要指缓存之后的小头训练快。
- batch=2/4 的特征提取反而更慢，当前采用 batch=1。
- 在线小头路线仍需运行 Qwen，仿真响应均值 3.33 秒；原始 VLM 直接生成约 8 秒。
- 监控状态里的 `elapsed_s` 因监控启动较晚，不等于全部特征提取耗时，不能用它覆盖上述实测累计时间。

检查过模型、处理器和分词器的固定版本一致性，未发现混用版本。缓存生成重复运行得到一致输出；无缓存对照约 93 秒只生成 26 tokens 后结束，未完成语义对照，因此没有证据把当前问题直接归因于 KV 缓存错误，也没有证明缓存与无缓存完全等价。

## 运动控制和高效采集已经解决到什么程度

### 直线运动

目标线速度为前后左右，不保证实际轨迹笔直。当前实现采用逐方向实测前馈、50 Hz 航向反馈及必要的正交速度补偿。前馈命令如下，单位为 m/s、m/s、rad/s：

| 方向 | vx | vy | wz |
|---|---:|---:|---:|
| 前进 | 0.20 | 0.00 | -0.10 |
| 后退 | -0.20 | 0.02 | 0.00 |
| 左移 | 0.00 | 0.20 | 0.28 |
| 右移 | -0.02 | -0.20 | 0.02 |

八秒留出初态测试中，最大侧偏由前进 40.3 cm、后退 15.5 cm、左移 79.8 cm、右移 44.6 cm，分别降为 6.2、2.5、8.4、8.6 cm。漂移明显减小但没有归零，航向保持也不能独立消除侧滑。配置绑定行走权重并标记 `hardware=false`，不能直接当成实机标定。

### 找球与踢球教师

当前策略是局部视觉闭环：先搜索并朝向目标，短段前进时不断修正目标方位，遇到可见其他球做简单避让，丢失目标重新搜索；进入可踢范围后站稳、重观察、选脚并踢球。

这是无地图的局部视觉伺服，不是 A*、全局最短路径或一般障碍物规划。目标通常保持在前进方向附近，临近踢球时允许必要的横移或后退，不能理解成任何场景都只直走。

可踢范围放宽为一个实测区域，而不是反复追求某个精确对齐点：身体坐标前向约 0.075 至 0.105 m，按左右脚转换的横向约 -0.003 至 0.055 m。放宽的是执行前对齐条件；验收仍要求目标脚接触、球移动至少 0.12 m、没有误碰其他球或提前推球、没有跌倒并恢复站稳。

相同九个任务上，新旧教师均 9/9 成功，平均路径由 1.490 m 降至 0.798 m，平均仿真时间由 38.751 s 降至 10.424 s，平均决策数由 55 降至 18.67。最终有限场景测试为 30/30，其中 18 个为最后调整后的留出任务。这些是规则教师成绩，不能归给 VLM，也不能外推为任意环境 100% 成功。

### 队列与动作连续性

按最新需求，当前在线执行器的能力快照为 `max_goals: 15`：单次计划最多15个目标，追加后的 `active + pending + 新增` 总数也最多15。合法的15项目标完整保留；16项或累计超限整组拒绝，不静默截断。旧显式 `max_goals: null` 仅保留为历史接口兼容，不能由用户文字把当前容量改为无限。聊天不清空任务；追加不重新启动当前动作；失败清空剩余队列。持续行走必须位于计划末尾，不能在其后排永远执行不到的步骤。

此前 Q0/Q1 冻结训练数据、开发集和成绩仍对应旧六目标规则，Q1 权重没有为此次15项容量或安全暂停规则重新训练，不能直接作为新规则的成绩。旧 GRU 小头的六步输出结构也保留为历史基线。生成式模型仍受上下文和输出 token 预算约束；协议接受7至15项不表示旧模型已学会这些长度。后续训练需使用独立版本的数据和评测，并覆盖15项接受、16项拒绝及追加总数边界。

Q1 目前训练的是 `decision + goals`，没有训练自然语言 `reply`。选中的 checkpoint100 在 240 条开发输入中，对 20 条应只回答、不启动动作的案例均输出正确的 `respond` 和空目标；这些包括能力问句、否定动作、假设举例和执行中问名字。这是任务决策成绩，不是回答内容的质量成绩。旧 selector 的回复来自规则或模板，旧 VLM 后端能直接生成回复，但已有样例存在空泛应答和视觉事实错误；开放多轮聊天尚未单独验收。

安全暂停保留未完成队列：有限目标完成整个动作及稳定恢复后，再挂起尚未执行的目标；持续行走在短段边界收稳后，保留同一持续目标。恢复只接着保留的队列，不重演已经完成的动作；最后一项已完成则回到空闲。推理期间的暂停只锁存请求，不打断推理，新计划生成后完整保留为暂停状态，不先执行第一项。停止／取消会撤销任务并清空队列，已取消任务不能用“继续”恢复。坐姿执行其他运动需先站起。

**当前两种 toy 模型后端都使用锁步仿真，推理时物理时间暂停。** 这使 3 至 8 秒推理期间观察不会随运动过期，但不是真机“边执行边推理”。旧 v2 曾实现后台续接框架，不能据此声称它已接入当前对话模型流程。

明确的“停/停下/停一下/别动/不用做了”等输入现在先锁存取消信号，不等待模型推理、普通输入队列或仿真世界锁；取消当前目标并清空余下目标。停止前排队的旧指令和迟到模型计划按取消代次作废，已取消任务不能用“继续”恢复，停止后新的明确任务仍可执行。嵌套踢球控制器保留父任务的取消标记，不能自行清除。

上述行为已覆盖阻塞推理、长队列、暂停后取消、迟到反馈和入口调度的并发回归，并通过仿真停止/坐姿保持回归。当前验证的是文本输入和本地执行链路；语音识别耗时、真实停稳时延、独立控制进程与看门狗仍需单独验证，不能据此声称真机已能边执行边推理或立即停稳。

## 仿真信息与附件带来的迁移问题

旧路径中球的位置由 RGB-D 感知计算，不直接把隐藏世界坐标作为规划输入，身体姿态和静止状态仍含理想仿真观测。
新 `rgb_tof_*` 支路使用 RGB、粗测区距离、IMU 和关节反馈；球位移和接触真值仅用于独立验收。
按“低头看球、计算球相对脚的位置、进入可踢范围就出脚”的改进已完成：
编码器足部正运动学替代近脚精确点对齐，并以当前 RGB 球弧＋至少两个当前 ToF 区处理球与红脚轮廓连通。
冻结 v6 的固定四场景、同四场景的 5 mm 噪声/10% 丢测、八个扩展位置分别为 4/4、4/4、8/8，
共 16/16 实际踢中并恢复站立，无提前推球或误碰其他球；235 项相关回归通过。
这是 12 个位置上的开发回归，不是任意场景或真机 100% 的证明，也不是 Q0/Q1 语言模型的成绩。
足前 6 cm 的校准曾出现提前擦球，右脚 12 cm 曾踢空；当前技能的可踢范围须实测，不能一味追求更近。
详见 [RGB/ToF 仿真报告](RGB_TOF_SIM_ZH.md) 与 `outputs/rgb_tof_20261116/FOOT_REACH_SUMMARY.json`。
未来实机仍需对应传感器、标定和状态估计，不能假定这些信息零误差可得。

现有实机部署代码已由 IMU 加速度/角速度融合输出重力方向并计算倾角；近似停稳可以结合 IMU 与关节反馈估计，
但不等价于直接读取仿真基座线速度。脸部激光测距为 RGB 距离估计提供了实际传感器来源，仍需完成目标关联与标定。

场景仍保留之前叼取实验的可动下喙和夹持垫。夹持垫尺寸参考 [microduck-beak-throw](https://github.com/llama/microduck-beak-throw) 的固定修订，可动下喙另参考 [microduck-with-rss](https://github.com/KeplerC/microduck-with-rss)，再进行了本地 HD1910、质量、碰撞和舵机适配；不是原版固定嘴机器人天然自带的结构。

当前训练在技能选择和对话层，因此无需直接学习夹具控制，但附件仍可能改变画面、遮挡、接触与动力学。尚没有“同一测试去附件后”的对照，不能把影响较小的直觉写成已经证明无影响。最终目标如果是不带附件的小鸭，应固定最终机器人模型与相机配置，再检查是否需要重采或混合外观数据。

## 并行采集和存储

本机实测过 1、2、4、8、12、16 个规则采集进程。对于同一三目标踢球基准，8/12/16 路约为 3133/3412/3467 段每小时；正式 582 段混合课程使用 8 路约 219 秒完成，二者任务组成不同，吞吐不能直接互相替代。

日常可用 8 路，专用采集可用 12 路；16 路测试通过，但相对 8 路增益有限。这是规则教师加仿真的能力，不代表能同时运行 16 个 VLM。更高并发未测试。

单纯用相同课程再换随机种子，会增加场景样本，但不会自动增加语言模板和任务组合覆盖。下一轮扩大数据前应先修正采样设计。

已进行的空间清理包括：

- 旧低效导航的 RGB、深度和轨迹大文件，约 10.03 GiB；保留了摘要、部分旧导出和模型，并非删除了昨天所有内容。
- 旧 Qwen3-VL 合并权重、多精度 ONNX 转换和专用环境，约 11.49 GiB；与 19 MiB 量级的低层动作 ONNX 完全不同。
- 训练与运行接口不匹配的旧数据和特征，约 298.9 MiB。旧 v2 对齐后 102 条验证数据仍保留，与当前 toy 数据不同代。

当前正式数据约 0.96 GiB，Qwen 基础权重约 4.3 GiB，全部历史实验 outputs 约 7.6 GiB。采集器默认有磁盘和内存阈值；仍应优先存决策边界图像及紧凑轨迹，按需渲染视频，避免无差别保存所有高频深度帧。

## 下一轮实验应保留的条件与指标

建议先固定当前模型、协议、执行器和测试记录，修正数据分布后做小规模对照，再决定扩大采集或切换路线。以下是待讨论的实验安排，不是已经完成的改进。

- 同一指令覆盖首轮直接请求、问候后请求、执行中请求、坐姿/站姿、已有任务/空队列等条件。
- 保留否定、能力问句、真正动作请求、未支持动作、目标歧义和中途纠正；不要把近义词替换当成全部语言多样性。
- 加入相同图像不同指令、相同指令不同目标位置与状态；避免颜色与位置、脚或动作顺序固定关联。
- 同一输入对比规则教师、当前小头、原始生成模型和候选改进，使用相同执行器与验收标准。
- 新建未参与调参的测试集，分别覆盖未见表达、未见场景、未见组合及中断；小规模历史诊断不能替代最终测试。
- 分开报告每回合应答、视觉事实、决策、完整计划、真实任务完成、错误启动、漏停止、虚假完成、延迟与峰值显存。
- 对真正异步方案额外测观察过期、停止响应、取消后旧计划复活、失败后恢复；锁步仿真成绩不能代替这些指标。

验收阈值还需要按产品需求确定。当前没有把任何一版模型宣布为可用成品，也不建议把同样有偏课程继续机械放大后就当作训练问题已解决。

### Q1R ONNX 导出测速（历史实验）

以下保留离线测速的复现方法。ONNX 桌面集成未完成，已按用户意愿搁置，当前桌面使用 PyTorch。
该历史实验命令从仓库根目录运行，不打开仿真或执行动作：

```bash
bash experiments/microduck_tasks/benchmark_q1r_onnx.sh
```

默认使用 `outputs/q1r_onnx_20261117/onnx_int8_fp16_head/` 和固定的 10 条真实输入，
预热一次后各重复两次，另存带时间戳的 JSONL 和运行元数据。耗时包括输入预填充与完整生成，
不含模型加载和输入分词，不共享跨请求缓存。可通过脚本的 `--model`、`--inputs`、`--output`
和 `--repeats` 参数复测其他导出；已有结果不覆盖。该命令仅用于离线测速，当前日常桌面入口不使用它。

依赖隔离安装在 `.cache/microduck_head/onnx_deps`、`onnx_cuda` 和 `onnx_cudnn`，
原训练环境保持不变。当前机器已安装；重建这些目录时使用现有实验 venv：

```bash
.cache/microduck_head/venv/bin/python -m pip install --no-deps --no-cache-dir \
  --target .cache/microduck_head/onnx_deps \
  onnxruntime-genai-cuda==0.20.0 onnxruntime-gpu==1.32.0
.cache/microduck_head/venv/bin/python -m pip install --no-deps --no-cache-dir \
  --target .cache/microduck_head/onnx_cuda \
  nvidia-cublas==13.0.2.14 nvidia-cuda-runtime==13.0.96 \
  nvidia-cufft==12.0.0.61 nvidia-curand==10.4.0.35
.cache/microduck_head/venv/bin/python -m pip install --no-deps --no-cache-dir \
  --target .cache/microduck_head/onnx_cudnn nvidia-cudnn-cu13==9.13.1.26
```

`report.json` 汇总条件、结果与限制，`compare_int8_fp16_head.json` 保留逐次对比，
`dialogue_review_int8_fp16_head.json` 保留逐例回复审阅，`onnx_int8_fp16_head_manifest.json`
记录模型文件摘要和实际精度。普通 ONNX checker 不识别导出器使用的部分 ORT 算子；
本次通过的是实际 ORT CUDA 加载和生成测试，不声称支持任意 ONNX 运行时。
中间浮点合并权重在三版导出后清理以回收磁盘，原基座、LoRA、tokenizer、ONNX 文件和日志保留；
`merge_report.json`、`intermediate_cleanup.json` 和 `export_commands.json` 记录重建方法。

### 原生桌面试验台

在当前电脑的桌面会话中，从仓库根目录启动：

```bash
.cache/microduck_head/venv/bin/python -m experiments.microduck_tasks.toy_desktop --backend q1r
```

程序打开 MuJoCo 默认原生窗口与右侧灰色中文聊天框，无需浏览器。默认后端是 Q1R PyTorch，加载 `outputs/q1r_20261116/train/checkpoint_000513`；省略 `--backend q1r` 也使用同一后端。聊天框通过系统 `/usr/bin/python3` 的现有 PyQt5 运行；记录默认在 `outputs/toy_desktop_<时间戳>/`。程序检测到 NVIDIA EGL vendor 后自动使用它并取消软件渲染强制项，无需用户配置。`--backend teacher` 只用于规则调试。

画面按1倍时间逐帧显示动作，完成／失败消息来自真实执行验收；推理时仍冻结物理时间。单次计划及未完成队列最多15项。安全暂停等待有限动作完整结束并稳定后保留剩余目标，持续行走在短段边界站稳后保留同一目标；继续不重演已完成动作。停止／取消立即锁存并清空任务，旧请求和迟到模型输出不能恢复执行。

此次修复了两类“看不到动作”：原锁步执行快速推进且阻塞显示取样，现改为逐帧发布和1倍时间显示；软件取图耗时被踢球桥误当观测过期，现按同一仿真时钟检查图像年龄，仍保留0.3秒阈值。NVIDIA EGL 的双相机 RGB-D＋检测中位耗时实测约11毫秒，软件渲染约486毫秒。

同场景 CPU 复现“前滚翻→踢蓝球”两项通过，右脚真实接触蓝球、位移3.07米、无提前推球或误碰其他球且恢复站稳，见 `outputs/plan_guard_replay_20261116/reproduction.json`。这是未调用 Q1 的执行桥回归，不是100%成功率或新的语言模型成绩。

当前 Q1R 由模型生成结构化 `decision + goals` 和中文 `reply`，本次入口切换不涉及重新训练。默认控制仍使用旧 RGB-D 执行桥，新增 RGB＋ToF 支路尚未接入。ONNX 桌面集成实验已搁置，文件保留。旧 `python -m experiments.microduck_tasks.toy_web` 和本机 `http://127.0.0.1:8765/` 保留为可选浏览器调试入口，日常使用原生窗口。
